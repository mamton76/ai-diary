## Вопрос

От каких угроз AI Diary защищает содержимое дневника, и какие обязательные меры это даёт для operational state сервиса: drafts, local/server snapshots, AI run records, FTS-индекс, кэши, логи?

## Варианты

1. **Базовый облачный уровень.** Шифрование at rest средствами облака по умолчанию, TLS везде. Сервисные копии содержимого хранятся минимально и с ограниченным сроком. Содержимое не пишется в логи. Доступ к production ограничен владельцем.
2. **Базовый уровень плюс шифрование чувствительных полей приложением.** Тексты drafts, AI run payloads и индекс шифруются ключом из KMS (возможно, per-user). Утечка дампа БД или бакета без доступа к KMS не раскрывает текст.
3. **Клиентское (end-to-end) шифрование.** Сервер и Drive видят только шифротекст.

## Контекст

Источник: [ревью требований 2026-11-08](../../../audits/2026-11-08-requirements-review.md), находка C2. По `шифр|encrypt` во всём `docs/` нет ни одного совпадения.

**Что уже решено и не переоткрывается этим тредом:**
- [PQ-001](../01_PQ-001_source-of-truth/00_thread.md): canonical — user-owned файлы в Google Drive. Значит, Google уже хранит содержимое дневника в открытом для своего сервиса виде.
- DATA-002: данные можно смотреть вне приложения.
- [AQ-AUTH-002](../14_AQ-AUTH-002_google-oauth/00_thread.md): хранение refresh tokens, revocation и re-auth отнесены к **implementation/security details, не блокирующим MVP**. Этот тред не переоткрывает это решение, но NFR из него обязан покрыть и токены.
- [AQ-AUTH-003](../11_AQ-AUTH-003_multi-user-readiness/00_thread.md): multi-user с user-scoped operational state.
- Gate плана «Security»: «no diary content in debug logs».

**Почему вариант 3 почти несовместим с текущим продуктом.** E2E-шифрование ломает:
- DATA-002 — чтение файлов вне приложения;
- серверный AI-процессинг;
- серверный FTS-индекс (E1);
- Calendar Timeline (заголовки событий).

Если он нужен, это пересмотр PQ-001, а не уточнение.

**Где содержимое реально оказывается вне Drive** (по архитектуре и требованиям):
- operational DB (drafts по DATA-012, leases, jobs, proposals, AI run records);
- derived FTS-индекс;
- local snapshots в браузере (DATA-013);
- очередь команд (API-006A);
- логи;
- провайдер LLM (это отдельный вопрос [AQ-AI-006](../48_AQ-AI-006_sensitive-data-policy/00_thread.md)).

## Обсуждение

Claude — Ответ на этот вопрос сильно зависит от того, **от кого** защищаемся. Поэтому первым шагом прошу задать модель угроз, а не выбирать технологию.

Мой анализ:
- Пока canonical лежит в Google Drive, защищать operational DB сильнее, чем сам Drive, имеет ограниченный смысл. Главные практические риски — утечка дампа или бэкапа сервисной БД, логов, или ошибка изоляции между пользователями при multi-user (AUTH-005).
- Поэтому рекомендую **вариант 1 как обязательный минимум для MVP** с четырьмя проверяемыми требованиями:
  1. содержимое не попадает в логи и трассировки (есть тест);
  2. у сервисных копий содержимого (drafts после Save, AI payloads, snapshots) есть явный срок хранения;
  3. refresh tokens хранятся только в зашифрованном виде через secret/KMS-хранилище облака, никогда в открытом виде в БД;
  4. есть тест изоляции пользователей.
- **Вариант 2** стоит заложить как «Later», на момент появления второго реального пользователя, а не одного владельца.
- **Вариант 3** — вне scope без пересмотра PQ-001.

**Нужно от пользователя:** подтвердить модель угроз — достаточно ли защищаться от утечки сервисной БД, логов и бэкапов и от ошибок изоляции между пользователями при доверии Google (Drive и Cloud). Или нужна защита и от самого облачного провайдера, что ведёт к варианту 3 и пересмотру PQ-001.

Claude — **Ответ на вопрос пользователя:** да, большую часть можно хранить в Google Drive пользователя, и это хорошо сочетается с PQ-001. Но не всё.

| Данные | Можно в Drive? | Комментарий |
|---|---|---|
| Server draft | **Да** | [AQ-DATA-010](../04_1_AQ-DATA-010_autosave-working-state/00_thread.md) уже допускает, что draft «физически может жить в одном storage» с canonical. [07-file-format](../../07-file-format-v1-draft.md) §5 прямо предлагает durable Draft в файлах (`draft/DRAFT.json`, `draft/snapshots/`). Цена — частые записи autosave в Drive API, поэтому нужны debounce и квоты |
| AI run records и debug-копии prompt/ответа | **Да** | Где хранить run records — открытый [AQ-AI-003](../../04-open-questions.md#aq-ai-003--где-хранить-run-records); Drive — сильный кандидат. Очистка debug-данных (PRIV-006) тогда — удаление файлов в Drive |
| Proposals, routines, настройки | **Да** | Workflow definitions уже user-owned data рядом с дневником ([AQ-AI-002](../32_AQ-AI-002_workflow-definition/00_thread.md)) |
| Очередь команд | **Нет** | Нужен быстрый транзакционный store; данные в ней живут секунды или минуты до commit |
| Поисковый индекс | **Нет, но он derived** | Для поиска нужна БД; индекс можно в любой момент удалить и перестроить из Drive |
| OAuth refresh tokens | **Нет** | Токен нужен, чтобы попасть в Drive, поэтому хранить его в Drive нельзя. Только зашифрованное хранилище секретов на сервере |
| Local snapshots | **Нет** | Они по определению живут в браузере (DATA-013) |
| Логи | **Нет** | В них и так не должно быть содержимого |

**Что это даёт для AQ-SEC-001.** Если принять принцип «долговременные копии содержимого живут в Drive пользователя, а на сервере только кратковременное и derived», то на сервере остаются:
- очередь (секунды или минуты);
- derived индекс, который можно перестроить;
- токены.

Тогда базовый уровень защиты (вариант 1) становится ещё более достаточным: сервис почти не хранит долговременных копий текста.

**Цена и риски принципа:**
- больше обращений к Drive API (квоты, задержки autosave);
- технические файлы рядом с дневником нужно держать в отдельной подпапке, чтобы не мешать чтению вне приложения (DATA-002);
- удаление аккаунта на сервере не удалит эти файлы. Это нужно учесть в [PQ-013](../50_PQ-013_data-exit/00_thread.md): либо отдельная команда «удалить технические данные из Drive», либо они остаются у пользователя.

Место хранения run records при этом окончательно решается в AQ-AI-003, а не здесь. Здесь принимается только принцип.

**Решение:** [принято] (2026-11-08) Модель угроз: Google (Drive и Cloud) доверяем. Защищаемся от утечки серверной БД, логов и бэкапов и от смешивания данных разных пользователей. Принцип хранения: долговременные копии содержимого дневника — drafts, AI run records, debug-копии prompt и ответа, proposals, routines, настройки — живут в Google Drive пользователя, в отдельной технической подпапке. На сервере остаются только кратковременные данные (очередь команд), derived индекс, который можно перестроить, и OAuth tokens. Обязательный минимум для MVP — вариант 1: шифрование at rest средствами облака и TLS; содержимое не попадает в логи и трассировки (проверяется тестом); у серверных копий содержимого есть явный срок жизни или явная очистка; refresh tokens хранятся только зашифрованными в secret/KMS-хранилище облака; есть тест изоляции данных пользователей. Шифрование полей приложением (вариант 2) и end-to-end шифрование (вариант 3) в MVP не входят: вариант 3 требует пересмотра PQ-001. Оба записаны в parking lot FQ-SEC-001. Окончательное место хранения run records решается в AQ-AI-003 с учётом этого принципа; судьба технических файлов в Drive при удалении аккаунта — в PQ-013.
