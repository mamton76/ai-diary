## Вопрос

Как формализовать один normalized capture input, чтобы Telegram, Google Calendar, web и другие adapters не зависели от schema финальной Entry?

## Уже согласованный контекст

Product baseline: external source → normalized capture item → Inbox-to-Entry processing → canonical Entry. Raw capture сохраняется до последующей AI-нормализации; provenance и revisions должны оставаться доступными. Отдельная Entry и CaptureItem не одно и то же.

## Обсуждение

пользователь — «давай»

ChatGPT — Предлагаю разделять транспортный адаптер и canonical Entry. CaptureItem должен сохранять source identity / dedupe key, source type, received/source event timestamps, исходные text/media payload references и provenance, а также optional normalized/transcribed text. Данные могут быть неполными (например, только изображение, без текста). Не следует принудительно приводить timestamp сообщения к времени описанного события; событие определяется позже. Требуется решить, что делать с несколькими сообщениями одного сеанса capture.

**Нужно от пользователя:** CaptureItem представляет одно исходное сообщение/событие, а объединение нескольких CaptureItems в дневниковую Entry выполняется отдельной стадией, или один CaptureItem может включать сразу несколько сообщений одной сессии?

пользователь — «норм»

ChatGPT — Принят принцип гранулярности: один CaptureItem соответствует одному исходному сообщению/событию источника. Несколько CaptureItems могут быть позже сгруппированы или объединены в одну Entry отдельной стадией processing. Границы одной сессии не определяют атомарность записи raw capture; сохраняем каждую часть и provenance независимо.

**Частичное решение:** [принято] (2026-10-18) One source item → one CaptureItem; multi-item grouping/assembly before Entry separate from capture.

**Следующий вопрос:** какой минимальный состав обязательных полей для CaptureItem и как представлять отсутствующий текст / только медиа?

пользователь — «да норм»

ChatGPT — Принято: каждый CaptureItem обязан сохранять оригинальный payload сообщения (текст и/или исходные медиа-файлы), а транскрипция, нормализация и AI outputs — отдельные производные артефакты с ссылкой на исходный CaptureItem. Минимальный contract: внутренний id, source, optional sourceId, receivedAt, optional sourceTimestamp, content (текст и/или asset refs), source-specific metadata. Даты захвата и описанного события различаются. При отсутствии текста capture допустим. Идентификатор источника может отсутствовать; для надёжных повторных импортов нужно отдельно определить deduplication/idempotency policy.

**Частичное решение:** [принято] (2026-10-18) Сохранять оригинал каждой единицы capture как исходные данные; результаты обработки не подменяют оригинал, а ссылаются на него.

**Следующий вопрос:** при повторной доставке того же сообщения из Telegram/Calendar мы должны узнавать дубль и не создавать второй CaptureItem?

пользователь — «ну ладо ок»

ChatGPT — Подтверждено: если источник повторно доставил то же сообщение с тем же стабильным source ID, система использует source-specific deduplication key и не создаёт второй CaptureItem. Два сознательно отправленных пользователем одинаковых текста — разные сообщения и сохраняются оба. Для источников без стабильного ID fallback должен не смешивать самостоятельные сообщения; технический механизм уточняется при реализации.

**Частичное решение:** [принято] (2026-10-18) Idempotent import of repeated source delivery по уникальному идентификатору внутри источника; не дедуплицировать разные сообщения по совпадению текста.

**Следующий вопрос:** следует ли разрешать объединять несколько CaptureItems в одну Entry вручную, помимо возможной автоматической группировки?

пользователь — «да мне нравится что 2 опции, можно на объединении сэкномить»

ChatGPT — Приняты оба режима сборки: ручное объединение выбранных CaptureItems в одну группу/будущую Entry без обязательного платного AI-вызова; AI-assisted grouping, когда пользователь хочет помощь в подборе связанных элементов. Оба режима сохраняют независимые исходные CaptureItems и provenance. Экономия важна: автоматическое AI-объединение не должно быть обязательным условием для ручной группировки.

**Частичное решение:** [принято] (2026-10-18) Manual grouping без AI + optional AI-assisted grouping, с сохранением source identity и оригиналов.

**Следующий вопрос:** когда пользователь объединяет CaptureItems вручную, сразу создавать черновик Entry из их содержимого или сначала группу, из которой Entry создаётся отдельным шагом?

пользователь — «ну давай попробуем»

ChatGPT — Пробно принят вариант A для MVP: ручное объединение нескольких CaptureItems с доступным текстом/транскрипцией создаёт редактируемый Draft Entry с собранным содержимым и ссылками на все исходные CaptureItems. Это ещё не committed Revision: запись сохраняется только при явном Save в соответствии с ранее согласованной семантикой Draft/Save. Оригиналы не изменяются. Если транскрипций нет, источники остаются сохранёнными до обработки; не создавать выдуманный текст.

**Частичное решение:** [принято для MVP, можно пересмотреть] (2026-10-18) Manual merge → editable Entry Draft при доступном тексте, без обязательного AI и без автоматического commit.

**Следующий вопрос:** если объединённые сообщения содержат разные или противоречивые даты, показывать исходные timestamps и оставлять дату Entry на выбор пользователя, не угадывая её автоматически?

пользователь — «да»

ChatGPT — Подтверждено: в UI ручного объединения показывать sourceTimestamp/receivedAt каждого исходного CaptureItem; дата описываемого события — отдельное поле Draft Entry, выбираемое пользователем. Не угадывать event date автоматически по самому позднему/раннему сообщению, особенно при разных датах источников. Сохранённые source timestamps и их provenance не изменяются.

**Частичное решение:** [принято] (2026-10-18) Capture timestamps не тождественны event date; при manual merge дата Entry остаётся на выбор пользователя.

**Следующий вопрос:** когда убрать CaptureItems из необработанного Inbox — уже при создании Draft Entry или только после успешного Save/commit Entry? Если Draft отменён, CaptureItems должны оставаться доступными для повторной обработки. Исходные данные сохраняются в любом случае.

пользователь — «да»

ChatGPT — Подтверждён вариант B для ручного объединения: созданный Draft Entry сам по себе не переводит исходные CaptureItems из необработанного Inbox. После успешного Save/commit Entry связанные CaptureItems отмечаются как обработанные и перестают отображаться в списке необработанных. При отмене, удалении несохранённого Draft или ошибке Save исходные CaptureItems остаются доступными для повторной обработки. Оригиналы не удаляются и сохраняют links/provenance к сохранённой Entry. Это правило относится к ручному draft flow; автоматическое создание первой Entry из raw capture уже отдельно разрешено в product policy.

**Частичное решение:** [принято] (2026-10-18) Pending Inbox → processed после successful Entry Save, не после Draft creation; source items retained.
