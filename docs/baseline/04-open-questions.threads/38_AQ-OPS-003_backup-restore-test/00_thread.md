## Вопрос

Как проверять восстановление пользовательских canonical files/revisions, индексов и UI после потери derived state или восстановления из backup?

## Контекст

В source AQ-OPS-003 перечислены шаги: потерять derived state; восстановить canonical storage/backup; перестроить индексы; открыть entries в UI; убедиться в сохранности provenance/revisions. AQ-OPS-002 уже определяет safe retries и экономный default для неопределённых платных AI вызовов.

## Обсуждение

пользователь — «да думаю так»

ChatGPT — Уточнение принято как операционное требование к recovery/retry: restart должен восстанавливать pending technical jobs через durable state/queue; платный AI call с неопределённым исходом не отправлять заново по умолчанию. Однако исходный AQ-OPS-003 посвящён также проверяемому backup/restore drill, решение по частоте/моменту такой проверки пока не обсуждалось.

**Нужно от пользователя:** для MVP достаточно выполнить один документированный restore test перед использованием реальных данных, а регулярную автоматическую проверку резервных копий оставить на будущее?

пользователь — «мне кажется нужно уметь воспроизводить восстановление»

ChatGPT — Принято как требование: не разовый ручной тест, а воспроизводимая процедура восстановления из canonical files/backup. Предлагается хранить в repo документированный runbook и скрипты/команды, которые восстанавливают пользовательские данные в отдельное место, пересоздают derived indexes и проверяют наличие entries, revisions и provenance. Процедура должна быть безопасной для действующего дневника и доступной для повторного запуска. Точный способ автоматизации и периодичность проверки ещё не утверждены.

**Нужно от пользователя:** достаточно ли воспроизводимой документированной процедуры и команды проверки по запросу, или восстановление нужно также регулярно тестировать автоматически по расписанию?

пользователь — «давай пока по команде»

ChatGPT — Принято: восстановление и его проверка должны быть воспроизводимыми по команде, без scheduled restore drill в MVP. Runbook/scripts в repo; проверять восстановление canonical entries, immutable revisions, provenance, assets, восстановимость derived indexes и доступность данных через UI/API. Тест проходит в изолированном location, не перезаписывая действующие данные. Само наличие backup недостаточно; требуется проверка результата.

**Решение:** [принято] (2026-10-18) Документировать и автоматизировать воспроизводимый on-demand backup/restore test с проверкой полноты canonical files, revisions, provenance и вложений, пересозданием derived indexes и доступностью entries в UI/API. Тест выполняется по команде и безопасно изолирован от рабочего хранилища; регулярный запуск по расписанию пока не требуется. Автоматическое восстановление безопасных technical jobs при рестарте согласовано; платный AI call с неизвестным исходом не повторять автоматически при default экономии токенов.
