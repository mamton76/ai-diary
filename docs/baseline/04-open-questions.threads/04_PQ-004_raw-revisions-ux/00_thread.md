## Вопрос

Как raw source и revision history должны быть представлены пользователю в обычном web UX?

## Варианты

1. **Всегда видимо** — raw/revisions являются обычной частью entry screen.
2. **History/Details on demand** — основной экран показывает current entry, а raw/revisions доступны отдельным действием.
3. **Только при проблеме** — raw/revisions всплывают при conflict, AI proposal, restore/review.
4. **Гибрид** — history доступна всегда, raw спрятан глубже; при conflict/AI proposal нужная версия показывается явно.

## Контекст

Хранить raw и revisions мы уже считаем обязательным. Здесь решается не сохранность данных, а степень их видимости в обычном пользовательском интерфейсе.

Первый web slice уже определён как browse/read/search; editing + versioning/history идёт следующим этапом. Поэтому этот вопрос влияет на UX второго этапа, но не блокирует первый read/search slice.

### Сводка 2 — Entry UI и семантика revisions

В качестве рабочей UX-модели обсуждается разделение текущего состояния записи и её истории:

- основной tab **Entry** показывает актуальную запись и доступные действия над ней;
- отдельный tab **History / Revisions** показывает происхождение и историю изменений записи;
- на desktop history не обязана постоянно занимать место рядом с записью: отдельная вкладка выглядит предпочтительнее;
- raw/original остаётся доступным через историю, но не обязан постоянно отображаться на основном экране.

По revisions появилась более определённая позиция:

- любое AI-действие, которое **изменяет существующую запись**, должно создавать отдельную revision;
- предыдущая версия при этом сохраняется, чтобы действие AI было прозрачно и обратимо;
- правила для manual edits пока не решены;
- не хочется определять «малое» и «большое» ручное изменение эвристикой по количеству символов или семантической величине изменения;
- рассматривается модель, где autosave отвечает за сохранность текущего working state, а revision является более осмысленной исторической границей;
- один из кандидатов для manual edits: одна завершённая editing session = одна revision;
- важный пограничный случай: если после несохранённой/незавершённой ручной правки запускается AI mutation, текущее ручное состояние должно быть зафиксировано так, чтобы его можно было восстановить перед применением AI.
