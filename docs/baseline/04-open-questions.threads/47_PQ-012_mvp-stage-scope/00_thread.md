## Вопрос

Какой документ задаёт **единственную каноническую таблицу этапов** продукта (web E0–E4, интеграции, AI) и какие из уже подтверждённых «тяжёлых» требований действительно входят в ранние этапы E0–E2?

## Варианты

Часть A — где живёт каноническая таблица этапов:

1. **Screens Spec §3** — каноническая. Inventory и product baseline ссылаются на неё, WEB-003 переписывается.
2. **Новая продуктовая таблица в 03-product-baseline.md**. Она покрывает web, backend, интеграции и AI. Screens Spec §3 остаётся детализацией по экранам и ссылается на неё, план P0–P7 сопоставляется с этапами.
3. **План реализации** (`implementation-plan-web-mvp.md`) — каноническая. Требования ссылаются на фазы P0–P7.

Часть B — у каждого требования появляется поле «Этап» (E0 / E1 / E2 / E3 / E4 / Интеграции / Later). Затем по списку «тяжёлых» требований решается, остаются ли они в раннем объёме.

Источник вопроса: [ревью требований 2026-11-08](../../../audits/2026-11-08-requirements-review.md), находки C1 и H18.

**Сейчас граница описана по-разному:**

## Обсуждение

Claude — Предлагаю разделить вопрос на две части. Сначала зафиксировать, **где** живёт канон, и только потом по списку решать, **что** в него входит. Иначе таблица этапов снова разъедется по трём документам.

Рекомендую **вариант 2**. Аргументы:

1. Граница этапов — продуктовое решение, и по README baseline она должна жить в product baseline. Screens Spec по своей природе описывает только экраны и не может честно задать этап для Calendar Timeline, Telegram или multi-user isolation.
2. Самую подробную работу уже сделала таблица Screens Spec §3. Новая таблица в 03 не должна её переписывать: она добавляет строки для не-экранных возможностей и ссылается на §3 за деталями экранов.
3. План реализации отвечает на вопрос «в каком порядке строим», а не «что входит в продукт на этапе». Если сделать канон в нём (вариант 3), каждое изменение порядка работ будет менять требования.
4. Поле «Этап» у пункта inventory позволит механически находить расхождения: например, WEB-003 и SEARCH-001 сразу покажут, что противоречат таблице.

Вариант 1 проще всего по объёму правок, но оставляет интеграции и backend без явного этапа.

По части B у меня нет позиции «выбросить». Многие пункты дешевле заложить сразу, например user-scoping данных в AUTH-005. Но AI-026/027 и OPS-004 стоит явно отнести к E4, а не к «MVP вообще». Это я предложу отдельной репликой после решения по части A.
