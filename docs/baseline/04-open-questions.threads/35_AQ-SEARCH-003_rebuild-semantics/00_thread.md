## Вопрос

Как гарантировать, что derived search index можно удалить, полностью пересобрать из canonical files и проверить его согласованность с файлами?

## Контекст

AQ-SEARCH-001: native FTS выбранной operational DB; асинхронное обновление индекса после successful canonical commit, небольшая eventual consistency задержка допустима. Пользователь уже согласовал rebuild из canonical files, но способ consistency checking ещё не обсуждён.

## Обсуждение

ChatGPT — Предлагаю предусмотреть ручную полную перестройку search index и проверку согласованности: сравнение списка ID и версий/ревизий canonical entries с индексом, без необходимости создавать новый сервис; автоматические проверки можно добавить после MVP.

**Нужно от пользователя:** достаточно ли для первого этапа ручного rebuild и запускаемой по необходимости consistency check по entry IDs/revisions, без постоянной автоматической сверки?

пользователь — «эм. ну кажется все же по таймеру надо проверять обнволения и изапускать индексацию если были изменения после?»

ChatGPT — Согласен с дополнением: event-driven индексирование после committed write остаётся быстрым путём, а периодический scheduler делает reconciliation — ищет canonical entries, чьи ID/revision отличаются от indexed state, и запускает reindex только изменившихся/недостающих записей, также удаляет stale entries при удалениях. Полный rebuild остаётся отдельной recovery-командой и не запускается при каждом проходе. Для detection следует опираться на устойчивые revision/change markers (или на проверенный scan canonical storage), а не считать только время последнего запуска абсолютной гарантией.

**Нужно от пользователя:** принимаем ли периодическую автоматическую сверку плюс индексацию обнаруженных изменений, оставляя конкретный интервал на этап настройки реализации?

пользователь — «я думю регулярной проверики более чем достаточно раз в полдня и думаю это потмо докрутим (но только при словии что на сохранении есть форм индексации)»

ChatGPT — Подтверждаем два контура: после успешного сохранения canonical revision обязательно ставится задача на индексирование; scheduled reconciliation примерно раз в 12 часов обнаруживает пропущенные изменения и удалённые записи, запускает incremental reindex только при необходимости. Интервал и реализацию можно уточнить позже. Full rebuild из canonical files сохраняется как recovery operation.

**Решение:** [принято] (2026-10-18) Основной контур: автоматическое обновление derived search index после каждого успешного canonical Save/commit через очередь. Страховочный контур: примерно каждые полдня сверять canonical entries/versions с индексом и переиндексировать только изменившееся/отсутствующее, удалять stale documents. При необходимости полный rebuild из canonical data; подробная конфигурация и технические детали — при реализации.
