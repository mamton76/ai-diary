## Вопрос

Насколько AI Diary должен быть offline-first на текущем этапе, особенно с учётом того, что первая новая реализация сейчас начинается с web-интерфейса?

## Контекст

Старый Android-проект рассматривал offline-first как центральный принцип. Для AI Diary по-прежнему важно не терять capture при плохой сети, переживать временные сбои connectivity и не допускать тихой потери пользовательского текста.

При этом текущий этап продукта сместился к web-first реализации. Полноценный offline-first для web потребовал бы существенно более сложной локальной persistence/sync модели, очередей изменений, conflict-aware synchronization и дополнительного UX для конфликтов.

Важно различать:

- устойчивость к временной потере сети;
- сохранность введённого пользователем текста/capture;
- полноценное offline чтение и редактирование;
- последующую синхронизацию и разрешение конфликтов.

Это голосовой тред: разговор не стенографируется. В файл попадают только содержательные сводки и явно принятые решения.

## Обсуждение

### Сводка 1 — full offline-first можно отложить

Пользователь считает полный offline-first идеальным долгосрочным сценарием, но не обязательным для текущего этапа. Поскольку сейчас работа начинается с web-интерфейса, полноценное offline browsing/editing и conflict-aware sync можно перенести на будущее.

Для первого web MVP допустима **online-first** модель.

При этом желательно уже сейчас сохранить более узкое требование надёжности: временный сетевой сбой не должен приводить к тихой потере уже введённого пользователем текста. Механизм может быть существенно проще полноценного offline-first и уточняется отдельно при проектировании web capture/edit UX.

Архитектура не должна специально закрывать путь к будущему offline-capable Android/native client, но поддержка такого клиента не должна определять сложность первого web/backend implementation.

### Текущая рабочая позиция

- Web MVP: online-first.
- Full offline browsing/editing: позже.
- Conflict-aware offline synchronization: позже.
- Защита capture/введённого текста от кратковременных сетевых сбоев: сохранить как требование.
- Будущую offline-capable native/mobile архитектуру не блокировать необратимыми решениями.

Окончательное решение и перенос формулировок в product/requirements baseline будут сделаны после завершения обсуждения связанных архитектурных вопросов.

### Итог

Для первого web/backend MVP принимается online-first модель. Полный offline browsing/editing и conflict-aware offline sync откладываются. Уже введённый текст/capture не должен тихо теряться при кратковременной потере сети; safe retry и видимые failures обязательны. Архитектура не должна блокировать будущий offline-capable native/mobile client. Конкретный механизм autosave/local persistence/sync остаётся отдельным implementation/architecture вопросом.

**Решение:** [принято] (2026-09-26) Первый web/backend MVP — online-first; full offline-first отложен; защита введённого текста/capture от кратковременной потери сети обязательна.
