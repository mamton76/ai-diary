## Вопрос

Действующие Abacus Python-скрипты уже пишут реальные записи дневника в Drive, но не имеют атомарного commit и идемпотентного recovery.

1. Что делаем с ними **до** появления backend и storage v1?
2. В какой момент они **перестают быть писателями** canonical-данных (cutover)?

## Варианты

Часть A — режим до storage v1:

1. **Заморозка кода плюс операторские правила.** Скрипты не меняем. Оператор следует письменным правилам:
   - после сбоя `/sync2` не перезапускать без проверки `inbox/` и `entries/`;
   - не запускать `--apply-exact-duplicates`;
   - сверять результат с отчётом дубликатов в режиме report-only.
2. **Минимальный hotfix в отдельной ветке скриптов** с replay-тестом (шаги 1–3 аудита):
   - Entry ID детерминированно выводится из source ID;
   - raw переносится после записи Entry;
   - статусы `raw_imported / entry_committed / calendar_projected`.
3. **Остановить автоматический импорт** до storage v1. Capture продолжается в Calendar Inbox, события просто копятся.

Часть B — cutover (решается после A):

- скрипты становятся клиентами backend API (P1/P2);
- скрипты остаются писателями до переноса логики в Kotlin, но с maintenance lock на время миграции (DATA-009);
- другое.

## Обсуждение

Claude — Это не архитектурный спор, а управление риском на живых данных. Важна цена ошибки: дубль записи можно найти отчётом дубликатов, а потерянный raw из-за переноса до создания Entry найти сложнее.

**Рекомендую вариант 1 сразу и вариант 2 как следующий шаг.**
- Вариант 1 почти ничего не стоит и снижает риск с сегодняшнего дня. Правила стоит записать в README скриптов и в план P0.1.
- Вариант 2 стоит делать только с replay-тестом и на тестовом календаре и папке. Это ровно «один следующий шаг» из аудита, так что работа не пропадёт: те же fixtures понадобятся для P1/P2.
- Вариант 3 оправдан, только если дубли или потери уже случались и их сложно разбирать.

По части B моя предварительная позиция: скрипты должны стать клиентами backend API к моменту первого mutating release web-версии. Иначе два независимых писателя будут конкурировать за одни файлы без общей fencing-цепочки из 08. Но это следующий шаг.
