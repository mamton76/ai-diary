## Вопрос

Исходная формулировка в source: «До полноценного multi-provider AI нужно определить:
- что можно отправлять provider;
- надо ли подтверждение;
- как показывается provider;
- можно ли запретить отдельному workflow external AI;
- retention/logging policy».

## Варианты

Модель согласия на отправку содержимого дневника внешнему LLM:

1. **Одно явное согласие на провайдера.** При первом выборе модели этого провайдера пользователь видит, что и кому уходит, и подтверждает. Дальше каждый запуск показывает провайдера и модель, но не спрашивает заново.
2. **Подтверждение на каждый запуск** (или на каждую отправку новой записи).
3. **Согласие на провайдера плюс политика на уровне workflow.** Как в варианте 1, но у workflow есть флаг «разрешён внешний AI». Отдельные workflow можно запретить или ограничить (например, только метаданные без текста).
4. **Внешний AI выключен по умолчанию**, включается глобальной настройкой с разъяснением.

- **prompt injection** через текст записей, Telegram и Calendar: содержимое дневника попадает в prompt. AI-026 допускает AI-созданные executors, а PQ-005 разрешает auto-apply части изменений;

- **что хранится в AI run records** (AQ-OPS-001): полный prompt с текстом записи или только ссылки.

Технические правила, которые я предлагаю обсудить следующими репликами (пока это **не решения**):
1. В AI run records по умолчанию хранить ссылки на Revision и хеш контекста, а не копию текста. Исключение — явный debug-режим с ограниченным сроком хранения.
2. Требование к провайдерам: использовать API-режим без обучения на данных; retention провайдера показывать пользователю при согласии.
3. Prompt injection: текст записей всегда передаётся как данные, а не как инструкции. Изменения от AI, вызванные содержимым записи, не применяются auto-apply к другим записям и не меняют workflow и executors.

Claude — Фиксирую договорённость по модели согласия: **вариант 3**. Это одно явное согласие на каждого провайдера плюс политика внешнего AI на уровне workflow. Итоговое **Решение** запишу после второй части: правил о том, что и как отправляется, хранится и показывается. Все пункты source-вопроса должны получить ответ.

Предлагаю шесть правил:

1. **Уровни политики workflow:**
   - «полный текст» — заголовок, текст, теги, даты;
   - «только метаданные» — теги, даты, тип, без заголовка и текста;
   - «внешний AI запрещён».

   Default для новых workflow — «полный текст». Иначе основные AI-сценарии (нормализация, теги) не работают. Пользователь может понизить уровень.
2. **Согласие на провайдера:**
   - экран согласия показывает, какие данные уходят, имя провайдера и его условия хранения и обучения;
   - согласие можно отозвать в настройках; после отзыва запуски с моделями этого провайдера не диспатчатся и получают понятный статус;
   - смена условий провайдера или новый провайдер требуют нового согласия.
3. **Как показывается провайдер:** провайдер и модель видны при запуске, в статусе job и в деталях run.
4. **Retention и logging:**
   - AI run records по умолчанию хранят ссылки на Revision и хеш переданного контекста, а не копию текста;
   - полный prompt и ответ сохраняются только во включаемом debug-режиме, со сроком хранения 7 дней (как у orphaned uploads в FQ-08/SQ-05);
   - текст записей не пишется в технические логи — это уже gate плана.
5. **Требование к провайдерам:** используются только API-режимы, в которых данные не используются для обучения. Если провайдер так не умеет, его модели не предлагаются.
6. **Prompt injection:**
   - текст записей, Telegram и Calendar передаётся модели как данные в отделённом блоке, а не как инструкции;
   - результат AI, вызванный содержимым одной записи, не может через auto-apply менять другие записи, workflow, executors, capability profiles или настройки;
   - такие изменения возможны только через proposal и review (уточнение к PQ-005).

Claude — Фиксирую: правила 1–3 и 6 приняты.

**Правило 4 в редакции пользователя:**
- полный prompt и ответ сохраняются только во включаемом debug-режиме;
- автоматически они **не удаляются**;
- у пользователя есть явная команда очистки сохранённых debug-данных.

Следствия, которые предлагаю учесть при переносе (это не меняет выбор):
- debug-копии — серверные копии текста дневника, поэтому на них распространяется минимум защиты из [AQ-SEC-001](../49_AQ-SEC-001_content-protection/00_thread.md);
- рядом с командой очистки полезно показывать объём и количество сохранённых debug-данных;
- при удалении аккаунта ([PQ-013](../50_PQ-013_data-exit/00_thread.md)) они удаляются вместе с остальным operational state.

**Пояснение к правилу 5.** Когда AI Diary отправляет текст записи модели, провайдер (OpenAI, Anthropic, Google) получает его на свои серверы. Дальше важны две вещи из условий провайдера:

1. **Обучение.** Может ли провайдер использовать присланные тексты, чтобы обучать будущие модели. По опубликованным условиям у платных API OpenAI и Anthropic данные по умолчанию для обучения не используются. У Google Gemini API бесплатный уровень разрешает использовать данные для улучшения продуктов, а платный — нет. Условия меняются, поэтому их нужно проверять при подключении провайдера; это не вечная гарантия.
2. **Хранение.** Даже без обучения провайдер обычно хранит запросы какое-то время (часто около 30 дней) для контроля злоупотреблений. Полный отказ от хранения (zero data retention) обычно доступен только по отдельной договорённости.

Правило 5 решает, что делать с моделями, условия которых разрешают обучение на данных. Варианты:
- **5a, строго.** Такие модели и уровни в AI Diary не предлагаются вообще. Например, бесплатный Gemini API для текстов дневника недоступен.
- **5b, с предупреждением.** Такие модели доступны, но экран согласия (правило 2) явно говорит «этот провайдер может обучаться на ваших записях», и пользователь подтверждает отдельно.

Срок хранения у провайдера в обоих вариантах показывается на экране согласия и не блокирует использование.

Я рекомендую **5a**: дневник — самые чувствительные данные (PRIV-001), а экономия на бесплатном уровне не стоит того, что записи попадут в обучающий набор.
