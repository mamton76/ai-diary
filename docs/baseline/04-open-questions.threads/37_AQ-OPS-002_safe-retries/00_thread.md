## Вопрос

Для каждого external/background workflow определить deterministic source identity, safe retries, partial failures и предотвращение дублей. Отдельно различать технический retry и сознательный rerun.

## Обсуждение

пользователь — «давай обсудим - кажется спорным»

ChatGPT — Рекомендация об идемпотентности всех операций чрезмерно широкая. Следует различать повтор запроса, повтор AI вычисления и повторный commit. Retry одной операции с тем же operationId не должен дважды применять side effects; rerun по инициативе пользователя с новым ID может дать новый результат. Read/fetch и derived indexing можно повторять автоматически; повторный LLM вызов может иметь новую стоимость и отличающийся ответ. Необходима отдельная политика для ambiguous outcome, когда запрос провайдеру отправлен, но ответа или подтверждения нет.

**Нужно от пользователя:** разрешить ли автоматический повтор вызова AI после временной ошибки/таймаута, или такие случаи показывать как неопределённые и предлагать ручной rerun?

пользователь — «наверное это дожно быт ьв настроках пользователя . и по дефолту навернео пока выбираем экономию токнеов»

ChatGPT — Принята принципиальная политика: автоматический повтор потенциально платного LLM вызова — пользовательская настройка; default экономит токены/стоимость. При неопределённом исходе LLM запроса по умолчанию не делать новый платный вызов автоматически; показать статус и дать пользователю возможность вручную повторить. Безопасные технические повторы доставки команд, чтения, индексации и недублирующего commit — отдельная категория и не должны отключаться вместе с AI retries. Настройку можно позднее расширить режимом с ограниченным числом платных повторов/бюджетом. Точные UI формулировки и границы надёжно распознаваемых неотправленных запросов уточняются при реализации.
