## Вопрос

Первый обсуждаемый подпункт FQ-08: что делать с **новым полностью загруженным managed original**, добавленным через Draft, если пользователь затем нажал Discard? Текст/изменения Draft отменяются; судьба загруженного файла пока не определена.

Остальные части FQ-08 — Entry permanent-delete dependencies, lifecycle после Restore, audit retention, partial staging cleanup и external originals — этим выбором не закрываются.

## Варианты

1. **Рекомендация:** сохранить готовый файл в библиотеке Asset без отменённой Draft-связи. Если связей с Active Entries нет, файл виден в Unlinked по принятому определению этого фильтра. Не удалять и не отправлять в Trash автоматически из-за Discard; пользователь может использовать его позднее или отдельно удалить из библиотеки.
2. Новые uploads, созданные именно для отменённого Draft, отправлять в Asset Trash, если проверено отсутствие других удерживающих references. Готовый Asset, ранее выбранный из библиотеки, не затрагивается. Permanent delete не происходит автоматически.

## Контекст

- FQ-03/SQ-01 принял: Save disabled до готовности всех оставленных attachments; Draft содержит готовые links, upload intent/status и references на загруженные originals.
- Пока Draft/операция актуальны, связанные originals/staging удалять нельзя.
- Unlinked означает отсутствие Active Entry links; это не доказательство отсутствия archived/history/Draft references и не критерий безопасного удаления.
- Выбор существующего библиотечного Asset и новый upload — разные источники.
- Discard не должен удалять Asset, используемый другой записью, другим актуальным Draft, history или незавершённой операцией.
- Неизвестный исход Save сначала согласуется с operation receipt; нельзя принять состоявшийся commit за отменённый Draft и удалить его attachments.
- Варианты относятся к законченному original. Неполные байты не превращаются в готовый Asset; сроки cleanup частичных загрузок остаются отдельным техническим остатком.
- Late upload callback после Discard не восстанавливает отменённый Draft и не создаёт молча новую Entry/Revision. Итог полностью законченного original должен следовать выбранной retention policy.

## Обсуждение

пользователь — (2026-10-18) «что дальше»

Codex — (2026-10-18) По текущему Save пользовательские подпункты закрыты, физический adapter spike остаётся на технической стороне. Следующая продуктовая развилка FQ-08 — судьба загруженного файла после Discard. Рекомендую сохранить готовый original в библиотеке, без отменённой связи с Draft; при отсутствии Active links он показывается как Unlinked. Это предложение, ещё не принятое требование.

пользователь — (2026-10-18) «по-моему как везед у нас - если это еинственная связь ассета то предлагать его удалить, если их несколтко прост орвем связь»

Codex — (2026-10-18) Принят пользовательский условный вариант: при единственной связи предложить удалить Asset; при нескольких снять только текущую. Безусловно оставлять все uploads в Library или автоматически отправлять их в Trash не выбрано. Под удалением сохраняется уже принятый soft delete; permanent delete остаётся отдельным действием. При отказе от предложения удаления Asset остаётся в Library без снимаемой связи.

**Техническая конкретизация:** Проверяются логические потребители по разным entryId во всех lifecycle-состояниях, в других Draft и связанных незавершённых операциях; исторические references других Entries не теряются. Несколько Revision/Draft одной и той же Entry не считаются отдельными записями; historical link той же Entry сам по себе не запрещает предложить soft delete, поскольку история/links сохраняются. При Discard рассматриваются только связи, реально исчезающие относительно восстанавливаемой Current: Asset, остающийся в Current, не является кандидатом на удаление из-за Discard. Проверка актуальна перед выполнением; при новой чужой связи выполняется только unlink. Состояние Unlinked по Active-счётчику не используется как доказательство единственности. Незавершённая операция с неизвестным исходом сначала требует reconciliation.

Codex — Первоначальное упоминание history среди удерживающих ссылок не должно считать каждую Revision той же Entry отдельным потребителем и блокировать предложение soft delete навсегда. Soft delete сохраняет ссылки/историю. Решение перенесено в Functional/Screens Specs, file-format / Save design и inventory/product baseline. Этот узел завершает обсуждавшийся подпункт готовых вложений; остальные части FQ-08 остаются в source открытыми, особенно late completion/partial uploads.

Codex — (2026-10-18) Следующий самостоятельный подпункт общего FQ-08 обсуждается в [SQ-01 — lifecycle после Restore](01_SQ-01_restore-lifecycle/00_thread.md). Этот узел остаётся resolved по вопросу готовых Asset после Discard/unlink; принятое решение не меняется.

Codex — (2026-10-18) Открыт отдельный [SQ-02 — удаление external original](02_SQ-02_external-original-delete/00_thread.md). Этот root остаётся resolved по готовым вложениям после Discard/unlink; новая рекомендация ещё не принята.

**Решение:** [принято] (2026-10-18) При снятии связи Asset с записью, в том числе при Discard добавлений Draft, применяется одно правило: если снимаемая связь единственная, предложить удалить сам Asset; если есть другие логические связи, снять только текущую без предложения глобального удаления в этом flow. Удаление — только по явному подтверждению и означает soft delete в Asset Trash, не permanent delete. При отказе от удаления связь всё равно снимается, Asset остаётся в библиотеке; при отсутствии Active Entry links он виден в Unlinked.
