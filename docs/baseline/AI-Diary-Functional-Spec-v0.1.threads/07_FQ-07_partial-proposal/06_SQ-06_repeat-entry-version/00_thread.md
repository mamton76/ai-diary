## Вопрос

При новом пользовательском продолжении/полном повторе прежнего batch, если Entry успели изменить, анализировать актуальную committed Revision либо исходный content snapshot прежнего запуска?

Пример: batch остановлен; одну из ещё необработанных записей пользователь исправил и сохранил. Затем запускает продолжение.

## Варианты

1. **Рекомендация:** актуальная committed Revision при фиксации input нового Run. Состав IDs остаётся прежним, анализ учитывает сохранённые исправления. После начала Run его input фиксируется, последующие изменения требуют обычной freshness/base проверки.
2. Исходный snapshot прежнего запуска, чтобы продолжение воспроизводило его старый input. Полученное предложение при изменённом Current может быть stale и требовать дополнительного review.

## Контекст

- [SQ-05](../05_SQ-05_batch-selection-snapshot/00_thread.md) уже фиксирует исходный список Entry IDs; он не выбирал frozen content.
- AI input — committed Revision; наличие WorkingDraft вызывает обычный skip/Save guard, несохранённые правки AI не забирает.
- Речь о новом явном пользовательском запуске, а не подмене input технического retry той же операции. Safe retry сохраняет operation identity и исходный input по уже принятому контракту.
- Новая committed Revision — новая input version для already-processed checks по прежнему AI-03. Если версия ранее успешно обработанной Entry изменилась, её нельзя считать already processed только по старой паре; точный UX отбора/объяснения skipped и changed Entries требует технической конкретизации.
- Текущий вопрос не выбирает версию инструкции routine при повторе; это отдельный аспект workflow versioning.
- Вариант 1 не разрешает обход lease/base checks или автоматическое применение stale результата.
- Точный момент input capture, manifest refs, attempt IDs и recovery относятся к техническому контракту.

## Обсуждение

Codex — (2026-10-18) Предлагаю при новом продолжении/повторе брать актуальный сохранённый content Entry: исправленный текст должен учитываться. После начала конкретного Run input фиксируется; технический retry не переключается на следующую Revision. Это рекомендация, ещё не принятое правило.

пользователь — (2026-10-18) «да»

Codex — (2026-10-18) Принята актуальная сохранённая версия Entry при новом продолжении/повторе. Ручные несохранённые Draft AI не трогает; технический retry не подменяет уже зафиксированный input. Решение перенесено в обе спецификации, inventory/product baseline. Остальные аспекты FQ-07 и workflow versioning не объявляются закрытыми. Следующий независимый продуктовый выбор — [FQ-06/SQ-06, lifecycle Home Calendar](../../06_FQ-06_updated-sort/06_SQ-06_home-calendar-scope/00_thread.md).

**Решение:** [принято] (2026-10-18) При новом явном пользовательском продолжении или полном повторе обработки существующих Entry берётся актуальная committed Revision каждой допущенной к обработке записи при фиксации input нового Run. Состав Entry IDs остаётся исходным. Несохранённый WorkingDraft не используется: действуют прежние Draft skip/Save guards. После фиксации input конкретного Run он не переключается на следующую Revision; технический retry той же операции сохраняет исходный input. Изменения Current после фиксации input обрабатываются прежними freshness/base/conflict checks.
