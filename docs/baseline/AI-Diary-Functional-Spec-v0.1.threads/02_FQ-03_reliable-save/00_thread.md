## Вопрос

Multi-file commit, recovery после частичного Save, idempotency и canonical location operational state: как не допустить расхождения durable Draft, новых tags и currentRevisionId после сбоя?

Обсуждение ведётся последовательно: сначала пользовательское поведение при потерянном подтверждении Save, затем конкретный commit/recovery protocol. Запись одной версии, отсутствие дубликатов и запрет silent overwrite уже требования; они не предлагаются как новые неподтверждённые возможности.

## Варианты для потерянного подтверждения

1. После восстановления связи приложение само выясняет исход исходной операции и при необходимости повторяет **ту же** операцию с прежним operationId и snapshot; commit возможен только при действительных base/ownership checks и если операция не отменена/не заменена.
2. После восстановления связи приложение показывает неопределённый результат; пользователь явно нажимает «Проверить / повторить». Проверка/повтор также идемпотентны, с тем же operationId. Без этого действия автоматического возобновления нет.

Ни один вариант не разрешает создавать новую Revision только потому, что ответ на первый Save потерялся.

- FQ-01 подтвердил Save/Apply/Restore и узкие AI auto-apply cases как commit paths.
- FQ-02 подтвердил catalog redirect merge без массовых Entry revisions; надёжная запись каталога также требует согласованности.
- Нужны различия: операция точно не завершена; commit подтверждён; исход неизвестен из-за timeout; conflict/утрата ownership.
- Путь к durable operation journal, точка публикации currentRevisionId, подготовка новых tags, возобновление после process crash и очистка staged files ещё не определены. Приведённый ниже порядок — предложение, не готовый утверждённый физический алгоритм.

## Обсуждение

пользователь — (2026-10-18, порядок тем) «**Revision/Save/Apply/Restore**, затем **merge тегов**, после этого — протокол надёжного сохранения.»

Codex — (2026-10-18) Предлагаю вариант 1: при потере ответа на Save после восстановления связи автоматически проверять исход той же операции; если commit уже произошёл, вернуть его Revision, а не создавать новую. Если не произошёл, повтор допускается только для того же зафиксированного snapshot/operationId, с проверками base/lease и отсутствия отмены/замены операции. При conflict повтор не перезаписывает чужие изменения.

Предложение для последующего technical design: фиксировать input snapshot и operationId, подготовить все данные Revision и необходимые каталожные изменения, публиковать только целостное новое состояние, после подтверждения очищать только сохранённый Draft и обновлять derived index. Сбой до публикации не должен открывать пользователю половину новой версии; сбой после публикации не должен приводить к дубликату при retry. Как обеспечить это в конкретных файлах, включая каталог и меняющийся Draft, ещё предстоит выбрать.

Если исход неизвестен, UI сообщает «Проверяем сохранение», а не ложное «Сохранено» или безусловное «Не сохранено». Новый ручной ввод и cleanup нельзя смешать со snapshot уже отправленного Save.

пользователь — (2026-10-18) «то что ты предложила - норм отлчино»

**Согласованная часть FQ-03 (2026-10-18):** Если подтверждение Save потеряно, приложение показывает «Проверяем сохранение» и после восстановления связи автоматически выясняет исход операции. При уже состоявшемся commit возвращается та же Revision; если commit не состоялся, безопасно повторяется та же операция с тем же operationId и зафиксированным snapshot. Повтор не создаёт дубликат и разрешён только при актуальных base/ownership checks, без отмены/замены операции. При conflict или потере права записи автоматический commit прекращается с понятным сообщением; введённые данные сохраняются. Неизвестный исход не выдаётся ни за успешное, ни за достоверно неуспешное сохранение.

Codex — (2026-10-18) Принят вариант 1 для потерянного подтверждения Save. Правило перенесено в source-документы. Физический multi-file commit/recovery protocol этим ещё не выбран, поэтому FQ-03 остаётся in_discussion.

Codex — Следующий пользовательский аспект: можно ли продолжать ввод, пока Save не подтверждён. Предлагаю разрешить редактирование: отправленный snapshot фиксирован, новый ввод остаётся в том же логическом WorkingDraft как более новое состояние и не попадает в retry старого Save. Подтверждение старой операции не должно очищать более новый Draft или отмечать новые правки committed. Вторая параллельная commit-операция по той же Entry не стартует до определения исхода первой; дальнейший Save использует новые правки и актуальную base Revision. Это предложение ещё не принято. Альтернатива — временно read-only editor до выяснения исхода Save.

Codex — (2026-10-18) Выбран более простой для первой версии вариант с временной блокировкой editor на Save; предложение разрешить параллельный ввод не принято. Продуктовое поведение перенесено в source-документы.

**Согласованная часть FQ-03 — editor во время Save (2026-10-18):** В первой версии после начала Save редактируемые поля этой Entry и повторный Save временно блокируются до определения результата операции. Просмотр, прокрутка и копирование текста доступны. При потерянном подтверждении действует автоматическая проверка/безопасный retry той же операции, статус «Проверяем сохранение»; редактор остаётся read-only. После подтверждённого успеха редактор доступен с сохранённым состоянием. После достоверного отказа без commit и без конфликта блокировка снимается, исходный Draft сохраняется для исправления/повтора. Conflict или утрата lease разрешаются соответствующим flow; сохранённый текст не очищается и право записи самовольно не восстанавливается. Продолжение ввода параллельно неподтверждённому Save в первую версию не включается.

Физический multi-file commit/recovery protocol ещё не утверждён. Остаются durable journal/operation record, commit publication, новые catalog tags, crash recovery и cleanup; ранее принятые automatic reconciliation, idempotency и отсутствие silent overwrite обязательны. Этот технический остаток нельзя объявлять закрытым из-за выбора UI-блокировки.
