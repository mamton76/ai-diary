## 1. Назначение и статус документа

Документ описывает набор пользовательских экранов, их структуру, общие компоненты, действия, переходы, состояния и критерии приёмки. Это спецификация интерфейса с необходимыми контрактами данных. Конкретный frontend framework и backend API не выбираются; согласованные правила хранения Draft и восстанавливаемого индекса включены, поскольку определяют сохранность и поведение UI.

Документ сохраняет весь обсуждённый интерфейс, но **не объявляет весь набор обязательным для первого релиза**. Этапы указаны отдельно.

Статусы положений:

- **[Б] Baseline:** подтверждённое требование или принятое решение в актуальных source-документах и тредах GitHub.
- **[Д] Диалог:** прямое пожелание пользователя из доступных обсуждений; его включение в конкретный этап реализации может ещё не быть согласовано.
- **[П] Предложение ТЗ:** конкретизация интерфейса в этом документе, которую нельзя считать ранее принятым пользовательским решением.
- **[О] Открыто:** необходимое уточнение или ещё не выбранный вариант.
- **[F] Future:** явно отложенная возможность.

В разделе со смешанным статусом положения помечены отдельно. Утверждение данного документа как нового baseline в GitHub не выполнялось.

**Принятая правка 0.2 [Д]:** нажатие на запись раскрывает её карточку прямо в списке для чтения и быстрых правок. Полный экран открывается отдельным действием из раскрытой карточки. Сворачивание или переход к другой записи с несохранёнными изменениями требует явного решения пользователя. Фильтры и позиция списка сохраняются. Эта правка заменяет прежнее предложение о прямом переходе из сниппета на S04; остальные продуктовые правила сохраняются.

## 2. Продуктовые принципы

1. **[Б]** AI Diary — персональная система памяти. Центральный объект — дневниковая запись `Entry`.
2. **[Б]** Сначала захватить, структурировать потом. Название, теги и сложные metadata не должны быть обязательным барьером для capture.
3. **[Б]** Чтение, создание и редактирование не зависят от доступности AI; наличие этих функций в конкретном релизе определяется этапом.
4. **[Б]** Исходные материалы сохраняются; AI не переписывает пользовательский текст молча.
5. **[Б]** Содержательное время события отличается от времени создания/обновления записи.
6. **[Б]** Текущая запись, рабочий черновик, AI-предложение и сохранённая версия — разные состояния/объекты.
7. **[Б]** Приложение адаптивное, online-first. Полноценный offline-first отложен, защита уже введённого текста обязательна.
8. **[Б]** У каждого пользователя изолированный дневник. Sharing и совместное редактирование не входят в MVP.
9. **[Б]** Canonical данные — переносимые файлы пользователя; Google Drive — первый storage backend. UI работает через backend/domain layer.
10. **[Б]** ZoomAlboom — отдельный будущий потребитель содержимого, не обязательная часть экранов AI Diary.

Источники: B02 — PROD, ENTRY, REV, DATA, OFF, AUTH; B03 — §§1–12, 18–21.

### 2.1. Канонические данные и disposable backend index [Д]

Source of truth — user-owned file storage, сейчас Google Drive. Backend DB/index/cache допустим для поиска, фильтров, relationships, Draft presence, routine history, proposals и derived review state. Все эти структуры disposable: их можно удалить и полностью перестроить из пользовательских файлов без потери пользовательских фактов. Durable Draft также хранится в этих файлах (§9.4).

Рядом с пользовательскими данными допустимы лёгкие derived index/checkpoint-файлы для cold start/rebuild; они тоже не authoritative. Технология индекса, invalidation и incremental rebuild остаются открытыми. Первый files-only этап E0 не запрещает ускоряющий индекс в следующих этапах.

## 5. Общие компоненты

### C01. EntryPanel — представление одного состояния записи [Б]

EntryPanel не владеет навигацией страницы, списком proposals, историей или списком AI runs. Он представляет конкретный snapshot записи.

| Область | View / historical / Base / Proposal | Edit / Result |
|---|---|---|
| Title | Отдельный заголовок | Отдельное редактируемое поле |
| Event time | Содержательная дата/интервал с точностью и timezone | C10 EventTimeRangeEditor: обязательная From date, optional From time и To |
| Text | Основной текст | Редактируемое содержимое |
| Assets | C11 AssetGallery связанных материалов | C12 AssetPicker для добавления; удаление связи; metadata файла — в Asset Detail |
| Tags | Связанные canonical tags | C09: chips, autocomplete имени/aliases, explicit create, unlink |
| Created / Updated | Всегда видимая, визуально вторичная read-only metadata | Не редактируется |

Адаптация определяется **шириной самого EntryPanel**:

- широкий panel: Title/Event time сверху; Text в основной колонке; Assets, Tags, затем secondary timestamps — справа;
- узкий panel: Title/Event time → Text → Assets/Tags → secondary timestamps;
- точный порядок Assets/Tags между собой, breakpoint и пропорции — implementation details;
- три узких panel на широком review screen должны переходить в stacked content layout, даже если весь viewport широкий.

Полная структура используется в view, manual edit, history comparison и proposal review. Expanded card и Full Entry Screen редактируют один и тот же набор: Title, Text, EventTimeRange, Tags и Asset links; оба используют общий working draft (C02). Нельзя создавать для review упрощённую копию, теряющую дату, материалы или теги.

**[П]** Пустое необязательное поле показывается спокойно, без требования заполнить его. Для отсутствующего title допустим отображаемый fallback «Без названия»; он не записывается в данные как реальное название без пользовательского действия.

### C02. EntryListItem — свёрнутая и раскрытая карточка [Д/П]

Карточка/строка списка: содержательная дата/интервал, title или fallback, короткий фрагмент текста, компактные теги, индикатор материалов, индикатор актуальных AI-предложений. Технические timestamps не заменяют дату события.

Наличие рабочего черновика, неподтверждённой даты или ошибки обработки отображается отдельным понятным индикатором, а не единым неясным статусом «AI».

**[Д, правка 0.2]** Нажатие на свёрнутую карточку раскрывает её на месте для чтения и быстрых правок. Раскрытая карточка содержит отдельное действие «Открыть полностью», ведущее на S04.

**[Д, уточнено приложенным источником]** И в expanded card, и на Full Entry Screen редактируются **Title, Text, EventTimeRange, Tags и Asset links**. Chips тегов — под текстом; C09 одинаково работает в обоих местах. Полный экран нужен для длинного текста, подробной работы с материалами, proposals, history и compare; он не является единственным местом редактирования даты и материалов.

В карточке меню `⋯`: Archive, Delete, submenu **AI / Run routine** для routines одной Entry. Небольшое действие Compare может открыть полный экран сразу в compare mode. Одновременно раскрыта только **одна** карточка; раскрытие другой означает сворачивание текущей с общим dirty guard.

**[П]** Карточка использует общую модель EntryPanel и общие editor/draft rules. Открытие для чтения не начинает editing session: session начинается с первой фактической правки. Draft виден в свёрнутой и раскрытой карточке; текущая версия и её draft не дублируются двумя строками.

### C03. ProposalCard [Б]

Краткое описание предлагаемого изменения, затронутые поля и состояние актуальности. Бесконфликтная карточка: Применить / Отклонить / Подробнее. Устаревшая или конфликтная: Отклонить / Подробнее, без быстрого Apply.

**[П]** В карточке показать короткое before/after или summary изменений, причину и uncertainty, если они предоставлены workflow. Полные prompt/model/input/output доступны через details, не занимают основную карточку.

### C04. RevisionCard [Б]

Тип и время изменения, snippet, краткие сигналы изменений: текст, дата, `+2 тега`, `−1 материал`. Клик — S06. Последовательные manual revisions могут объединяться визуально в раскрываемую группу, сохраняя все revisions в данных.

### C05. Статусы сохранения и операций

**[Б]** Пользователь различает working draft и committed revision; видит последнюю синхронизацию draft, queued/running/done/failed jobs, потерю editing lease и ошибку операции.

**[П]** Примеры UI-текстов: «Есть изменения», «Черновик синхронизирован · 10:42», «Нет связи — изменения сохранены на устройстве», «Версия сохранена», «Редактирование продолжено в другой вкладке». Сообщение про локальное сохранение допустимо только после реального успешного local write.

### C06. Calendar — календарь записей [Д]

**[Д, 18.10.2026]** Calendar относит Entry к местной дате события в сохранённой timezone самой записи. Событие «19 октября, 00:30, Токио» показывается на 19 октября, даже если в пользовательской timezone в этот момент ещё 18-е. Выбор дня/диапазона в Calendar открывает список с той же семантикой местных дат и принятым period overlap; индикатор и список используют одинаковый lifecycle scope. Смена пользовательской timezone не переносит сохранённые события между днями Calendar. Date-only сохраняется как дата без выдуманного времени. **История:** [FQ-05/SQ-03](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/03_SQ-03_calendar-event-date/00_thread.md).

Общий виджет, используемый на Home: один месяц, стрелки переключения месяцев, сетка дней. Дни хотя бы с одной Entry просто выделены. **Counts и дополнительные state badges на календарь не добавляются.** Используется содержательное время события, не createdAt.

Клик по **любому** дню открывает Entry Browser с универсальным date range на этот день, включая пустой день. Создание записи выполняется отдельным `+ New Entry`, а не автоматически при выборе пустого дня. **Выбор диапазона дат поддерживается** и передаёт From/To в тот же Browser; точная механика выделения диапазона остаётся [О].

**[П]** Входы компонента: месяц, текущий день/выбранный диапазон, локаль/timezone, признак наличия записей по дням, область данных и loading/error state. События: смена месяца и выбор дня/диапазона; контейнер выполняет переход. Компонент не привязан к конкретному маршруту.

Загрузка, готовый месяц, месяц без записей, ошибка/повтор различимы; неизвестные данные не выдаются за пустые дни. Текущий день, выбор и наличие записей доступны не только по цвету/hover. **[О]** Единые правила попадания многодневных/приблизительных событий в дни остаются UI-Q02.

**Приёмка:** нет счётчиков/статусов в ячейках; клик по пустому дню даёт фильтр и empty-state Browser; день/диапазон и открытая выборка согласованы.

### C07. TagCloud — облако тегов [Д/П]

**[Д, правка 0.3]** Облако тегов — общий переиспользуемый компонент для обзора тем и перехода к связанным записям. Основное использование — S02. **[П]** При необходимости тот же компонент может использоваться в S08 или над другой выборкой; это возможность reuse, не требование добавлять его на каждый экран.

**Состав:** теги с названиями и настраиваемыми цветами; размер по числу связанных записей **[Д]**. Видимая подпись области данных, точное количество у тега/по focus и выделение выбранного тега — **[П]**.

**Входные данные [П]:** stable tag ID, имя, цвет, количество уникальных Entry для каждого тега; область подсчёта (весь дневник или явно выбранный период/фильтр), текущий выбор, loading/error state. Теги, ещё только предложенные AI, не входят в применённые связи и обычные счётчики.

**Правила отображения:**

- **[Д]** Больше записей — больший размер тега.
- **[П]** Используется единая монотонная шкала с ограниченными min/max размерами; равные количества дают одинаковый размер. При единственном теге или одинаковых количествах шрифт остаётся читаемым, без ошибки нормализации.
- **[Д]** Цвет хранится непосредственно у тега и настраивается в каталоге S08; optional type на цвет не влияет [Д, позднее решение 04.10]; **[П]** компонент получает готовый цвет и не генерирует случайный при каждом render. Предложение о хранении цвета в каталоге сохранено в S02/S08.
- **[П]** Теги переносятся по доступной ширине контейнера; длинные названия не создают горизонтальный overflow, полное имя доступно пользователю. Цвет не заменяет подпись или состояние выбора.

**Действия [П]:** выбор тега передаёт tag ID и область выборки экрану-контейнеру; в S02 открывается S03 с соответствующим отбором. При наличии действия «Настроить цвета» оно открывает согласованное место настройки. Компонент не владеет маршрутизацией, изменением каталога и логикой AND/OR фильтров.

**Состояния [П]:** загрузка, готовое облако, нет тегов в данной выборке, ошибка/повтор. Ошибка не подменяется пустым облаком. Для пустого облака видна область, в которой теги отсутствуют.

**[Д, 04.10] Подключение на Home:** все Active Entries за всё время, без Archived/Trash; используем текущее представление с WorkingDraft. Частота — число уникальных связанных Entry. Клик открывает Entry Browser с Active + выбранным tagId, без ограничения месяцем календаря. Цвет — свойство тега; type опционален и не управляет цветом. **[О]** Лимит количества тегов и порядок их размещения не подтверждены найденными сообщениями.

**Приёмка:** размер согласован с количеством Entry; цвет устойчив во всех представлениях; переход сохраняет область подсчёта; облако читаемо и управляемо на узком экране. Составные условия задаёт C13, а не собственная логика AND/OR облака.

### C09. TagInput / TagChips [Д; уточнения реализации отмечены отдельно]

- Ввод `#` в редактируемом тексте открывает popup у курсора. Поиск по префиксу canonical name и aliases без учёта регистра, с подсветкой совпавшего префикса; прямые совпадения canonical name выше alias-only matches; клавиатурная навигация — [П].
- Один canonical tag представлен одним результатом. При совпадении alias показывается, например, `#Обучение (Самообразование)`; выбор этого alias вставляет **`#Самообразование`**, но связь хранится с canonical `tagId`, а chip показывает canonical name `#Обучение`.
- Выбор существующего результата связывает тег с Entry. Новый создаётся только явным `Create #…`; произвольно набранный `#word` сам по себе не создаёт тег или связь.
- Под текстом chips связанных тегов; `+ Tag` открывает тот же popup без обязательной вставки в текст; `×` снимает связь.
- **Chips — источник истины связей.** Удаление `#alias` только из текста не снимает chip. При Save, если в тексте нет ни canonical hashtag, ни одного alias связанного тега, недостающие упоминания дописываются **в конец текста одной строкой через пробел**, отделённой от непустого body пустой строкой; заголовка «Tags:» нет. Уже написанные canonical/alias mentions не перемещаются и не дублируются; повторный Save не добавляет повторную строку. Это заменяет раннее правило «удаление последнего hashtag отвязывает тег».
- **[Д, подтверждено приложенным источником]** Созданный из Entry новый тег до Save живёт в WorkingDraft; canonical tag попадает в каталог при успешном Save; Discard не оставляет созданный таким способом тег в каталоге. Операция должна быть согласована с успешностью Save.
- **[Д, 18.10]** После `×` при Save упоминания снятого тега/aliases преобразуются в `#_name`: текст остаётся пригодным для поиска, но не выглядит и не обрабатывается как активный тег. Если chip вернули до Save, пометка снятия не применяется. Повторный Save не добавляет `_` ещё раз. **[Д, 18.10]** Разделитель linked hashtags — один пробел; строка в конце отделяется от непустого body пустой строкой (§26.13).

### C10. EventTimeRangeEditor [Д]

**[Д, 18.10.2026]** У интервала записи с From/To, заданными датами без времени, последний указанный день To включается целиком в пользовательском смысле. «Поездка 1–10 июля» видна и при выборе 10 июля. Date-only верхняя граница фильтра «по 10 июля» также включает весь указанный день. Сохранённые значения остаются date-only: фиктивные 00:00/23:59:59 в EventTimeRange не записываются. **История:** [FQ-05/SQ-05](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/05_SQ-05_date-only-end-inclusion/00_thread.md).

**[Д, 18.10.2026]** Отсутствие To у Entry означает одиночное событие на указанную From дату/время, без автоматического продолжения до текущего дня или в будущее. Если указана только дата, дневной Calendar и связанный date filter относят запись к этой местной дате без выдуманного времени суток. Если задано время, опорой служит указанный момент без придуманной длительности. Это правило не меняет односторонние границы query filter. **История:** [FQ-05/SQ-04](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/04_SQ-04_missing-event-end/00_thread.md).

From date обязательна для завершённого значения; From time необязателен. To целиком необязателен, To time также необязателен; заданный конец не предшествует началу. Date-only сохраняет точность даты и не превращается в `00:00`. Один timezone ID на интервал (например, `Europe/Belgrade`), default из настроек пользователя, если задан, иначе из устройства; timezone редактируемая, хранится и для date-only и версионируется вместе с EventTimeRange. Единая логическая структура — `from`, `to`, `timeZone`; физическая сериализация не фиксируется. Изменение даты/времени/timezone входит в WorkingDraft. Неполный ввод сохраняется как draft, не выдаётся за валидный диапазон.

**[О]** Привязка многодневных/неопределённых событий к дням, смешанная точность концов и физическая схема хранения не определяются этим UI-контрактом.

### C13. FilterBuilder / FilterChip [Д]

**[Д, 18.10.2026]** Запись с известной датой, но без времени суток, включается в фильтр по часам того же дня как возможное совпадение. Например, «18 октября» без времени попадает в «18 октября, 12:00–14:00». В результате сохраняется явная пометка «время не указано»; запись не получает выдуманные часы, длительность на весь день или новое content-значение. **История:** [FQ-05/SQ-06](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/06_SQ-06_date-only-clock-filter/00_thread.md).

Hybrid UI: активные фильтры всегда видны как chips; кнопка **Filters** добавляет/редактирует условия. Desktop — popover/side panel; mobile — bottom sheet. Условие `field + operator + value` представлено chip; группа рекурсивно содержит условия/группы. **AND, OR и общее NOT доступны сразу**. По умолчанию добавляемые условия объединяются AND. Группа отображается и редактируется как одно составное условие с доступной внутренней структурой.

| Поле / предикат | Контракт |
|---|---|
| Text contains | По title + body; обычный текстовый поиск. Regex — future |
| Event date/time range | Универсальные optional From/To; каждая граница содержит date, optional time, timezone; обе — период, только From — после, только To — до |
| Tag | Canonical tagId; aliases разрешаются в тот же ID; свободный текст не выдаётся за совпавший тег |
| Has draft / Has assets | Yes / No |
| Has open AI proposals | Отдельный Yes / No; proposals ещё не приняты и не отклонены |
| State | Active / Archived / Trash; задаётся явным условием или preset |
| Source | Web, Android, Google Calendar, Telegram, Import и другие источники |
| Needs attention | Наличие unresolved review item: proposal, conflict или uncertainty; не новый lifecycle state |

Сортировки: Event date, Updated, Created — по возрастанию/убыванию; Title — A–Z/Z–A. Default — Event date newest first.

Предварительный минимальный каталог системных presets: Drafts, Archived, Trash, Needs attention, Open AI proposals, Entries with assets, Last 7 days, Last 30 days; динамические входы Calendar, TagCloud, Statistics создают такой же фильтр. Ранний label Needs review заменён Needs attention. Пользователь выбирает preset в Entry Browser; ручное изменение превращает его в обычный текущий фильтр, не переписывая системный preset. Текущие фильтры — ephemeral screen state; сохранение контекста переходов не превращает их в сохранённый preset. Custom Saved Filters отложены. Раздельные title/body filters, regex и date shortcuts вроде «July 2026» — future; shortcuts внутри преобразуются в универсальные From/To.

Определения системных presets живут в `_system/` **пользовательского хранилища данных на Drive**, отдельно от Entries, и мигрируют с форматом данных. Это не каталог исходного Git-репозитория. Точная сериализация — implementation detail.

- Полноценный Compare доступен только на Full Entry Screen; маленькое действие из expanded card открывает его сразу в compare mode. Proposal review сохраняет собственные три роли Base/Result/Proposal (S07).

- **[Д]** Фильтры и позиция списка сохраняются при раскрытии/сворачивании карточки, переходе к другой записи и возврате с полного экрана. **[П]** Повторная загрузка страницы восстанавливает поддерживаемый контекст по URL или другому устойчивому механизму.

### Раскрытие, быстрые правки и переход на полный экран

**[Д, принято 28.09.2026]** Основной сценарий: список → раскрытая карточка для чтения/быстрых правок → при необходимости отдельное действие «Открыть полностью» → S04 для длинного текста, материалов, предложений AI и истории. Основное нажатие на сниппет не открывает popup и не уводит со списка.

**[Д]** Если в карточке есть несохранённые изменения, сворачивание и переход к другой записи требуют явного решения пользователя. Такое же решение требуется при уходе с нового unsaved Entry screen; без изменений переход выполняется без диалога. Autosave working draft не равен Save committed revision и сам по себе не отменяет это требование. Ни сворачивание, ни переключение не должны молча сохранять revision или отбрасывать изменения.

**[Д, 04.10]** Явный выбор: **«Сохранить» / «Отменить изменения» / «Вернуться позже»**.

- Сохранить — успешный commit новой revision, затем переход/сворачивание; при ошибке остаёмся с draft.
- Отменить изменения — удалить working draft, вернуть последнее committed состояние; новая несохранённая Entry исчезает как отменённый draft. Новая revision не создаётся.
- Вернуться позже — оставить working draft и разрешить уход; это не «Остаться» и не commit. При возврате пользователь продолжает draft.

**[П]** Закрытие самого диалога без выбора сохраняет исходную карточку и правки.

**[Д]** Переход на полный экран той же Entry продолжает ту же editing session/working draft без отдельной копии и без автоматического commit только из-за смены представления. Передача draft не должна терять локальные изменения; если продолжение не удалось, переход не маскирует ошибку. Общие lease/version checks обязательны.

**[Д]** После возврата с S04 восстанавливаются фильтры и позиция списка. **[Д]** Восстанавливаются также сортировка и раскрытая карточка той же Entry. Если сохранённая запись перестала соответствовать фильтру или сменила место сортировки, список сохраняет ближайший устойчивый scroll anchor и объясняет изменение; точная реализация — UI detail.

**[Д]** Одновременно раскрыта только одна карточка. **[Д]** В expanded card редактируются Title/Text/EventTimeRange/Tags/Asset links, как и на полном экране (C02). В E0 карточка доступна для чтения; быстрые правки включаются в E2 вместе с versioning и защитой draft.

### Режимы lifecycle

| Режим | Состав [Б/Д] | Действия [Д], при включении lifecycle UI |
|---|---|---|
| Active filter | ACTIVE | Открыть, редактировать, архивировать, переместить в корзину |
| Архив | ARCHIVED, исключены из явно Active-выборок | Открыть, вернуть в активные |
| Корзина | DELETED / Trash, soft-deleted | Восстановить; Delete permanently |

**[Д]** Archive / Restore / Delete меняют lifecycle metadata и audit history, **не создают content Revision**. Archive Entry с Draft применяется ко всей Entry вместе с Draft, после короткого confirmation; при открытии archived Entry draft доступен для продолжения редактирования. Delete Entry с committed Revision перемещает всю Entry и Draft в Trash. Для новой Entry без committed Revision Delete может полностью удалить Draft/Entry.

В Entry Trash доступны **Restore** и **Delete permanently**. Автоматический permanent deletion timer пока не нужен. **[П]** Необратимое удаление требует явного подтверждения; его последствия для зависимых ссылок должны быть видны до выполнения.

Lifecycle не смешивается с обработкой AI, наличием draft или uncertainty. Постоянной категории Entry.DRAFT нет.

### Фильтры и presets

**[Д]** Entry Browser использует C13 целиком: рекурсивные AND/OR/NOT, text contains по title/body, даты, tags, draft/assets/open proposals, Source, lifecycle и Needs attention. Поля появляются с соответствующей функцией приложения. Пункт Main Navigation **Entries** открывает Browser **без фильтров**; All entries — отсутствие фильтров, не отдельный экран. Не добавляется скрытое State=Active. Active/Archived/Trash выбираются явным фильтром/preset; Home, облако и счётчики со своей областью передают её явно. Ручное редактирование preset создаёт обычный фильтр. Фильтры и сортировка сохраняются при переходах и раскрытии карточек.

### Состояния и приёмка

Отдельные состояния: загрузка; дневник пуст; нет результатов по фильтрам; недоступно хранилище; частичная ошибка списка. «Ничего не найдено» не подменяет сетевую ошибку. В E0 не выводится фиктивная строка работающего поиска. При возврате из записи сохраняются фильтры и позиция списка [Д]. Сворачивание dirty-карточки и переключение на другую Entry без явного решения пользователя запрещены [Д].

Быстрое чтение/редактирование остаётся доступным в списке. **[П]** Прямые ссылки на Entry продолжают открывать полный экран.

### 9.3 View и Edit

В view содержимое read-only. При edit становятся доступны соответствующие controls C01. Title остаётся отдельным от body; дата события редактируется отдельно от created/updated.

**[О]** Textarea, Markdown, rich text с Markdown-сериализацией или structured editor — выбор AQ-WEB-003, ещё не принят. ТЗ не требует конкретную библиотеку или сложную панель форматирования.

Manual content editing не должен незаметно превращаться в редактирование source/composition. Отдельный composition editor в текущий scope не включается.

### 9.4 Editing session, WorkingDraft и явный Save [Б/Д]

- Session начинается с первой фактической правки. Autosave синхронизирует WorkingDraft, **не создаёт committed revision**.
- **[Д, 04.10] Автокоммита по таймеру нет.** Правило «manual revision после часа inactivity» отменено. Manual revision создаётся только явным Save. **[Д, 18.10]** Подтверждённые Apply AI proposal и Restore исторической версии сразу создают по одной новой committed Revision; второй Save не нужен. Preview/редактирование Result до Apply commit не создаёт.
- WorkingDraft editable content включает Title, EventTimeRange (From/To/date/time/timezone), Text, Tags и **связи** Assets. Raw/provenance/history, AI proposals/results, ID/currentRevisionID/createdAt и bytes Asset не являются редактируемым content. Draft имеет собственные служебные baseRevisionId/updatedAt/session поля; это не изменение committed timestamps. Archive/delete — отдельные действия.
- Перед Save и передачей lease обязателен flush; ошибка не очищает draft. Успешный Save создаёт revision и удаляет durable Draft из пользовательского хранилища; recovery points живут по своей policy.
- **[Д]** Discard / «Отменить изменения» удаляет draft и возвращает последнее committed состояние. «Вернуться позже» оставляет draft без commit. Эти действия работают и в full editor.
- Открытие Entry с draft продолжает его с учётом lease. Draft обозначен в full editor, collapsed/expanded card и Home; доступен глобальный счётчик/фильтр Drafts.

**[Д, 18.10]** Manual Save без фактического изменения content завершает эквивалентный Draft без новой Revision (NO_CHANGE / существующая Revision, без изменения committedUpdatedAt). Неподтверждённый исход сохраняет Draft для проверки/retry. Применяется общая карточка решения из §8; переход на полный экран той же Entry продолжает тот же Draft. [FQ-03/SQ-02](AI-Diary-Functional-Spec-v0.1.threads/02_FQ-03_reliable-save/02_SQ-02_no-change-save/00_thread.md).

**[Д, 18.10]** При Discard готовых attachments действует общее правило: при единственной снимаемой связи предложить soft delete, при других — только unlink; без подтверждения Asset остаётся в библиотеке. Asset, присутствующий в восстановленной Current, не является исчезающим добавлением. **[О]** Cleanup незавершённых uploads/late callbacks и явно отброшенных local recovery points остаётся отдельным вопросом.

### 9.4.1. EntryVersion и физическое хранение Draft [Д]

Единая концептуальная модель **EntryVersion** со state **DRAFT / COMMITTED**: Draft изменяемый, committed immutable. В UI/history Revision означает только committed version. У Entry максимум один текущий Draft со ссылкой на base revision/version; это не Entry lifecycle DRAFT.

Draft — полноценные пользовательские данные в **user-owned file storage**, не только server working state. Хранится внутри папки Entry рядом с revisions: `entries/.../<entryId>/draft/DRAFT.json` и `draft/entry.md`; committed `ENTRY.json`, `entry.md`, `revisions/` остаются рядом. Это согласованное расположение; приведённые имена иллюстрируют формат, не фиксируют все поля будущей схемы.

Draft содержит **полный snapshot**, не diff. История autosave-снимков Draft не ведётся; локальные recovery snapshots — отдельная страховка (§9.5). Возможные metadata DRAFT.json: baseRevisionId, title, event time/timezone, tagIds, assetIds, собственный updatedAt и editor session fields. `draft/entry.md` содержит текущий editable text.

Autosave **не меняет** `ENTRY.json.currentRevisionId` и не отражается в `ENTRY.json.updatedAt` как committed change. Save создаёт новую immutable Revision с ID/номером, переключает currentRevisionId и только после успешного commit удаляет Draft. Discard удаляет Draft без content Revision. Badge Draft показывается только при существующем рабочем Draft; Saving… / Draft saved обозначают синхронизацию Draft, не Save revision.

### 9.4.2. Блокировка editor на время Save [Д, 18.10.2026]

В первой версии после начала Save редактируемые поля этой Entry и повторный Save временно блокируются до определения результата операции. Просмотр, прокрутка и копирование текста доступны. При потерянном подтверждении действует автоматическая проверка/безопасный retry той же операции, статус «Проверяем сохранение»; редактор остаётся read-only. После подтверждённого успеха редактор доступен с сохранённым состоянием. После достоверного отказа без commit и без конфликта блокировка снимается, исходный Draft сохраняется для исправления/повтора. Conflict или утрата lease разрешаются соответствующим flow; сохранённый текст не очищается и право записи самовольно не восстанавливается. Продолжение ввода параллельно неподтверждённому Save в первую версию не включается.

### 9.5 Recovery [Б]

Компактная шкала: previous revision → local snapshots → current draft. Previous/current — крупные точки, local snapshots — малые. Tap/hover раскрывает время и тип. Выбор snapshot сначала показывает preview; восстановление заменяет working draft и само не создаёт revision.

MVP policy defaults: до 5 local snapshots; не более 30 секунд между recovery points при изменении содержимого; retention 24 часа после успешной revision. Это configurable constants, не обязательные пользовательские настройки.

**[Д, 04.10]** При сворачивании/смене Entry действуют Сохранить / Отменить изменения / Вернуться позже (§8). Local snapshots предназначены только для recovery и не запускают автоматический commit. **[Д, 18.10]** Незавершённый merge draft в S07 автосохраняется и восстанавливается (§26.35); он не подменяет manual WorkingDraft.

### 9.6 Параллельное редактирование [Б]

- Для одной Entry один mutation owner; разные Entry редактируются независимо.
- Вторая session получает свежий durable Draft через backend, предупреждение и выбор: read-only / «Редактировать всё равно».
- Takeover передаёт lease новой session. Прежняя уведомляется и становится paused/read-only; её local unsynced changes остаются в recovery.
- Потерявшая lease session не может Save поверх чужих правок. Сначала повторное получение lease и синхронизация.
- Если current revision изменилась, UI показывает conflict/rebase flow, не last-write-wins.

### 9.7 Приёмка

После нескольких autosave и одного Save появляется одна manual revision. После перезагрузки доступен durable Draft из пользовательского file storage; локальное recovery не выдаётся за межустройственное хранилище. При конфликте ни старая вкладка, ни завершившийся AI run не перезаписывают новую версию молча.

## 10. S05 — Создать запись

`+ New Entry` есть как минимум на Home и в Entry Browser и открывает тот же Full Entry Screen с новым Draft. Минимальный сценарий: открыть → ввести текст → Save первой Revision. Пустой title получает отображаемый fallback, например первые слова текста, без записи fallback как настоящего title. **[О]** Допустимость пустой/asset-only записи уточняется при реализации.

## 11. S06 — Версия / Revision details

**Основа:** PQ-004, PQ-011, REV-007…015, WEB-016/017.

### Структура [Б]

- Предыдущая revision — слева, read-only.
- Выбранная revision — справа, read-only.
- Обе стороны используют общий C15 EntryCompare и EntryPanel/diff building blocks. C15 также поддерживает editable Draft справа при сравнении с base Revision; эта операция доступна в S04.
- Отдельный provenance/details block: origin manual/AI/import/restore, timestamp, previous/base revision, raw/source links, workflow/run/proposal references, restored-from reference — когда применимо.

По умолчанию сравнивается **предыдущая версия с выбранной**, а не current с выбранной и не original с выбранной.

### Diff [Б]

Text — читаемая подсветка изменённых фрагментов; точный алгоритм выбирается при реализации. Tags/Assets — добавления и удаления `+ / −`. Перестановка assets не считается изменением. Title и event time показывают изменённые значения. Created/updated и provenance не входят в content diff.

### Restore [Б]

Восстановление создаёт новую committed revision из snapshot выбранной версии; сохраняет связь с источником восстановления. Новейшие версии не удаляются. Восстанавливаются title, event time, text, tags, asset links и versioned source/composition state.

**[П]** Перед подтверждением показать, какую версию пользователь восстанавливает и что появится новая версия. Если есть dirty draft или чужая active session, сначала разрешить это состояние; не обходить общие mutation rules.

### Ограничения

- **[О]** У первой revision нет previous: рекомендован явный empty-state «Предыдущей версии нет», raw/source — отдельной ссылкой. Это UI-предложение, не уже принятое решение.
- **[Д, 04.10]** При permanent delete Asset сохраняется минимальная запись и нейтральный placeholder «Файл удалён», без preview. Restore revision возвращает ссылки, но не удалённые bytes. Soft-delete Asset допускает Restore из Trash (S09).
- **[F]** Compare with произвольной revision, отдельный сложный history workspace, ветки версий и compaction UI не входят в текущий этап.

### Приёмка

Нельзя редактировать historical panel напрямую, принять/отклонить revision или удалить одну revision. Apply и последующий Undo создают две исторические операции. Восстановление не меняет stable Entry ID.

## 12. S07 — Проверка AI-предложения

**Основа:** PQ-005, AI-015/020/021, PQ-011, DATA-015/018.

### 12.1 Быстрый путь на EntryScreen [Б]

Apply/Reject карточки относится ко всему proposal. До Apply content не становится current state и proposal не появляется в History как revision. Reject не создаёт фиктивную content revision, но outcome остаётся трассируемым.

Stale/conflicted proposal не имеет быстрого Apply. Несколько proposals могут существовать параллельно при совместимых scopes; один AI run может дать несколько proposals, один proposal — изменения нескольких полей.

### 12.2 Подробный путь [Б]

| Левая панель | Центральная панель | Правая панель |
|---|---|---|
| **Исходник (Base)**: состояние, от которого работал AI | **Результат (Result)**: реальное будущее состояние записи | **Предложение AI (Proposal)**: исходный AI результат |
| Read-only | Editable; изменения относительно Base подсвечены | Read-only; изменения относительно Base подсвечены |

Если Current совпадает с Base, начальный Result соответствует Proposal. Если Current уже менялся, Result учитывает совместимые текущие изменения; конфликт показывается в конкретном поле/фрагменте.

Пользователь может оставить Current, взять Proposal или вручную исправить Result. Хотя Current не является четвёртой постоянной колонкой, его значение должно быть доступно при выборе конфликтного участка **[П: конкретизация обязательного выбора Current]**.

Независимые изменения допускают deterministic merge. Это не разрешение на бесконтрольный auto-merge изменённого пользователем текста: при содержательных текстовых изменениях действует осторожная policy DATA-015.

### 12.3 Подтверждение [Б]

Подтверждение Result создаёт одну новую committed revision. До подтверждения это merge draft. Частичное принятие complex proposal возможно через редактирование Result.

Перед apply повторно проверяются ownership и base/current compatibility. Если запись изменилась, пока пользователь рассматривал proposal, устаревший Result нельзя записать поверх нового Current.

**[Д, 18.10.2026]** При частичном принятии и подтверждении Result proposal получает статус «Принято частично» и закрывается целиком. Непринятые части сохраняются в исходном Proposal/AI history, без pending-остатка или автоматически созданных новых proposals. Сам этот proposal перестаёт быть причиной внимания; другие причины Entry сохраняются. **История:** [FQ-07 — частичный Apply](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/00_thread.md).

**[Д, 18.10.2026]** Закрытие review без применения сохраняет исходный pending proposal; [незавершённый Result/merge draft автоматически сохраняется и восстанавливается](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/01_SQ-01_review-draft-resume/00_thread.md).

**[П, layout mobile]** На телефоне допустим последовательный выбор Base/Result/Proposal, если смысл ролей и возможность проверить результат не теряются; точная mobile parity трёхстороннего proposal review остаётся открытой; обычный Compare C15 уже имеет Before/After switch либо inline diff на mobile.

### 12.4 Приёмка

Нельзя применить stale proposal одной кнопкой на карточке. После Apply current state совпадает с подтверждённым Result. History содержит ровно одну новую revision, а AI activity связывает её с исходным proposal/run. Если применение не удалось, proposal не объявляется применённым.

## 13. S08 — Теги

**Основа:** TAG-001…006, WEB-011, PQ-003; поздние решения 04.10 [Д]. Самостоятельный top-level экран.

Каталог: canonical name, aliases, color, optional type, Entries count. Поиск по canonical name и aliases. Цвет хранится непосредственно у тега; type необязателен и не управляет цветом. Клик по тегу открывает редактирование; клик по числу Entries — Entry Browser с tagId. Счётчик: Active Entries с текущими Draft, без Archived/Trash.

| Действие [Д] | Результат |
|---|---|
| Create / Edit | Создать тег или изменить свойства; интерфейс Entry использует общий C09 |
| Rename | Stable identity сохраняется; прежнее имя добавляется в aliases |
| Add / Remove alias | Ручное управление aliases |
| Merge | Пользователь выбирает canonical; второй тег и его aliases становятся aliases выбранного; type/color выбранного canonical сохраняются |
| Delete | Soft delete; если тег используется — предупреждение и подтверждение; permanent delete тегов не вводится |
| Deleted / Restore | Удалённые скрыты по умолчанию; фильтр Deleted и восстановление |

**[Б]** Unlink из Entry — versioned правка этой записи; AI не удаляет user-added tags автоматически. Pending AI candidate не считается применённым тегом. **[Д]** Immutable Revisions при rename/merge/delete **не переписываются**. Подробности:

- Merge разрешает **текущие Entry/Draft relations** в surviving tagId через каталог, без физической перезаписи snapshots/Draft и без новых content Revision; имя второго и его aliases переносятся с дедупликацией. Старый tagId остаётся redirect `mergedInto` для разрешения historical revisions; второй тег перестаёт быть самостоятельным active tag. В merge-dialog нет дополнительных настроек type/color: берутся свойства survivor, меняются позже обычным editor.
- Delete сохраняет самостоятельный historical tagId со state deleted; старые Entry/Draft/Revision relations не меняются. Тег исчезает из autocomplete и обычного TagCloud, новые связи запрещены. Перед удалением используемого тега видны количество связанных Entry/Draft и confirmation; в history допустим приглушённый Deleted label.
- Удаление alias не меняет relations по tagId, влияет только на дальнейшие autocomplete/распознавание.
- Types — **пользовательский справочник**, не system enum; optional typeId, без color inheritance/override hierarchy.

**[Д, 18.10]** Дубли aliases между самостоятельными активными canonical tags запрещены; при конфликте показать существующий тег и не сохранять дубликат. **[Д, 18.10]** Canonical name и aliases также не пересекаются между разными самостоятельными активными тегами. Transfer обозначения сейчас не включён. **[Д, 18.10]** Уникальность и lookup names/aliases не учитывают регистр; выбранное написание сохраняется для отображения. **[Д, 18.10]** Name/aliases удалённого тега остаются занятыми без учёта регистра; при конфликте показывается удалённый тег и предлагается явный Restore вместо создания нового. Ввод имени сам по себе не восстанавливает тег. **[О]** Остальные правила Unicode/пробелов и точный historical rendering цвета/имени остаются деталями policy; запрет переписывать immutable snapshots уже принят.

### Приёмка

Rename сохраняет поиск по старому имени; alias разрешается в один canonical tagId. Merge сохраняет выбранные type/color и не удваивает Entry counts. Delete используемого тега требует подтверждения; Restore доступен. Каталог и облако используют одинаковые цвета и область счётчиков.

## 14. S09 — Материалы / Asset Library и Asset Detail

**Основа:** ASSET-001…009, REV-014, AQ-DATA-005; поздние решения 04.10 [Д]. Самостоятельный top-level экран; Picker вынесен в C12.

### Library [Д]

Все активные Asset, включая не привязанные к записям. Показывается число связанных **Active Entries**. Фильтр **Unlinked** выбирает ноль таких связей; название не означает физическое отсутствие ссылок в архиве или history. Список/grid с preview или fallback, именем, типом; available metadata — размер/длительность, managed/external. Поиск по имени файла и Asset name; для первой версии достаточно этого, Unlinked и Trash. Доступны upload/external link и выбор существующего; один Asset может быть связан с несколькими Entry.

Состояния upload/link: выбран → загружается/проверяется → готов; отдельно failed/retry и «Выберите файл повторно». Ошибка не изображается как доступный original. Managed original отличается от external reference; external original не обязан копироваться. **[Д, 18.10]** Save disabled до разрешения статусов всех оставленных вложений; текст продолжает autosave. Draft восстанавливает готовые Asset links и pending uploads с именами/статусами; загруженные originals сохраняются. Если недогруженный файл нельзя возобновить, pending attachment остаётся с действием повторного выбора. Thumbnail/preview не блокирует Save. [FQ-03/SQ-01](AI-Diary-Functional-Spec-v0.1.threads/02_FQ-03_reliable-save/01_SQ-01_upload-before-save/00_thread.md).

### Asset Detail [Д]

Клик по Asset открывает preview, имя, type, size, date, связанные Entries, **Link to Entry**, **Delete**. Можно переименовать Asset и редактировать необязательное **description**. Rename меняет metadata, сам файл не меняется. Дополнительное расширение библиотеки сейчас не требуется. **[П]** Возврат сохраняет выборку библиотеки; переход из связанной Entry использует её stable ID.

### Связи и удаление [Б/Д]

Из Entry действие `×` снимает текущую связь. **[Д, уточнение 18.10]** При единственной логической связи предлагается выбор «Удалить в корзину» / «Оставить в библиотеке»; при других связях выполняется только unlink. Это же правило действует для исчезающих добавлений при Discard Draft. Отказ от удаления сохраняет Asset в Library и не отменяет само снятие связи. Изменение связей входит в WorkingDraft; обычный editor не правит bytes/metadata файла, явное soft delete — отдельная подтверждённая операция. [FQ-08 — снятие связи / Discard](AI-Diary-Functional-Spec-v0.1.threads/04_FQ-08_discard-uploads/00_thread.md).

- **[Д] Delete = soft delete в Trash:** связи сохраняются; если Asset используется, предупреждение показывает последствия; доступен Restore.
- **[Д] В Trash: Delete permanently и Empty Trash** для освобождения места. После физического удаления Restore невозможен и preview не сохраняется; минимальная запись Asset и нейтральный placeholder «Файл удалён» остаются в Entries/старых revisions. История не обещает восстановления bytes.
- **[П]** Необратимое удаление требует отдельного явного подтверждения с областью действия; Empty Trash относится к корзине материалов.
- **[О]** Удаление внешнего original у стороннего провайдера не определено и не подразумевается удалением external reference. Срок хранения Trash и автоматически осиротевших загрузок не установлен.

### Приёмка

Unlinked Asset виден в Library. Soft delete сохраняет связи и допускает Restore. Permanent delete освобождает управляемый файл, оставляет минимальную запись/placeholder без preview; чтение исторической Entry не ломается. Rename/description меняют Asset через Detail, не превращаются в правку body Entry.

## 15. S10 — AI actions, activity и run details

**Основа:** AI-001…022, PQ-005/006, AQ-DATA-010, WEB-014/015.

### 15.1 Запуск из AI ▾ [Б]

Пользователь выбирает готовый workflow или Custom prompt / Ask AI. Workflow работает с committed revision. Если editor dirty, применяется **Save & Run**: сначала успешный Save, затем запуск от новой revision. При failed Save workflow не запускается по несохранённому тексту.

**[П]** Диалог запуска показывает выбранную запись/версию, workflow/instruction, эффективную модель и область данных, уходящих внешнему AI. Однократный выбор модели доступен как override; отдельный selector provider не нужен.

### 15.2 Jobs [Б]

- Состояния queued/running/done/failed видимы компактно; доступна отмена.
- **[Д, 04.10]** Общие/пакетные routines пропускают Entry с WorkingDraft; не ставят их в очередь до конца ручной session. Для явно выбранной текущей Entry сначала Save; при отказе/ошибке Run не стартует. Mutating workflow не вытесняет manual editor.
- Read-only/informational AI может работать без mutation lease.
- Пользователь может прервать AI mutation и начать редактирование. Отменённый job не получает право commit после потери lease, даже если внешний LLM request физически завершился.
- Закрытие страницы не уничтожает durable job. При новом открытии перечитывается актуальное состояние.

### 15.3 Activity и details

**[Б]** Из Entry доступен drill-down к полной AI activity, в том числе для rejected/failed/non-mutating runs, которые не создали revision.

**[П]** Список: workflow, время, status/outcome, модель, связанная Entry. Детали раскрывают:

- **[Б]** workflow/version, prompt/version, реально использованные provider/model;
- **[Б]** input/base revision и input references/snapshot;
- **[Б]** AIResult, validation, proposals и их resolution;
- **[Б]** созданные committed revisions, timestamps, при необходимости token/cost metadata;
- **[П]** понятную ошибку и допустимые действия retry/cancel/open proposal/open revision.

Информационный анализ остаётся workflow result и не превращается автоматически в текст Entry или постоянный AI-note.

### 15.4 Политика применения [Б]

| Тип результата | Базовое поведение |
|---|---|
| Информационный/производный анализ | Может создаваться автоматически, без изменения Entry |
| Первая normalized entry из raw | Может создаваться автоматически при сохранении raw и явной uncertainty |
| Привязка существующих тегов | Может auto-apply при высокой уверенности согласно workflow policy |
| Создание новых тегов | По умолчанию через proposal |
| Изменение существующего content/неоднозначных metadata | Persistent proposal; применение создаёт revision |
| Удаление user-added tags | AI не делает автоматически |

Способ применения USER/AUTO не заменяет lifecycle Proposal. Уже применённый auto-change — исторический факт, не «на проверку».

### 15.5 Что пока не включать

**[F]** Merge/split Entry, bulk AI mutation/delete, advanced model comparison и AI memory. **[О]** Inline assistance над selection/working draft — кандидат на editor slice; его undo/proposal/revision semantics ещё не определены. Он не подменяет Save & Run.

### 15.6 S13 — Routines [Д]

Обязательный самостоятельный экран: catalog of routines, запуск, создание и редактирование user routine, history/runs, результаты и статистика **processed / skipped / errors / time или duration**. Детали запуска переиспользуют S10. **[П]** Структура вкладок Routines / Runs (History).

System routines immutable; доступна Duplicate / Copy в пользовательскую копию с редактированием. Минимальная модель user routine: **name, description, prompt/instructions, scope/eligibility, application policy**. Точная форма и application policy остаются [О]; model preference продолжает общую иерархию настроек.

### 15.7. Точки входа, scope и повторные запуски [Д]

- Expanded card: `⋯` → **AI / Run routine**, применимые routines для одной Entry.
- Full Entry Screen: **AI ▾** → single-Entry routines и Custom prompt.
- Entry Browser: batch routine на **текущем filtered set**.
- Home: полного Routines widget нет. `+ Start AI` — future, обсуждается позже.

Selection scope при запуске (single Entry / current filtered set / all Entries) отличается от постоянных eligibility conditions внутри routine. Фильтры Browser дополнительно сужают набор; `filtered batch` — результат текущего filter expression. Entry с Draft пропускаются и учитываются в skipped. Для отдельной Entry сначала успешный Save; без него routine не запускается. AI input — committed Revision.

Для повторов используется существующая run/proposal/revision history: run связан минимум с **routineId, routineVersion, entryId, baseRevisionId/input Revision, result/status**. Обычный batch может skip уже успешно обработанную пару routineVersion + input Revision как already processed, независимо от Accept/Reject proposal. **[Д, 18.10]** Достоверно failed Run без успешного результата сам по себе не вызывает already-processed skip и допускает обычный повтор; платные автоматические повторы по-прежнему подчиняются пользовательской policy. **Force rerun доступен явно.** Новая Revision или routineVersion допускает обычный запуск.

Accepted и rejected proposals не исчезают из history. Accepted перестаёт быть open, сохраняет provenance и может ссылаться на созданную Revision.

**[Б]** Наличие batch launch не разрешает автоматически применять любые изменения: действует policy proposals/Apply. Bulk AI mutation/delete остаётся future; пользовательская application policy ещё требует конкретизации. Расписания/триггеры этим ТЗ не утверждаются.

## 16. S11 — Настройки и подключения

Группировка в одной странице — **[П]**; продуктовые контракты ниже — **[Б]**, если не указано иначе.

### Аккаунт и дневник

Состояние входа, Google Drive connection, возможность дать необходимый consent. Calendar — отдельное optional подключение. **[О]** Account switch/revocation/re-auth UX уточняется при реализации OAuth.

### AI

Иерархия effective model: override конкретного run → workflow preference → global user preference → system default. Основной сценарий — global preference. Provider определяется моделью.

Если модель недоступна, тихая замена другой моделью/provider запрещена. **[П]** UI показывает проблему и предлагает явный выбор доступной модели или повтор позже.

User instructions/overrides поддерживаются отдельно от стабильных system contracts. **[Д]** Создание пользовательских routines вынесено в S13 (§15.6). **[О]** Конкретные controls редактора и расширенные trigger/schedule возможности ещё не определены; разовый Custom prompt остаётся самостоятельным действием.

### Calendar

Не смешивать три сущности:

| Сущность | Роль |
|---|---|
| Календарь на Обзоре | Внутренняя навигация по Entry |
| Calendar Inbox | Внешний capture adapter, сырой вход |
| Calendar Timeline | Односторонняя производная проекция current committed Entry |

**[Б]** В timeline одна Entry соответствует одному event; новая revision обновляет event. Pending proposal не публикуется как текущее содержание. Projection можно перестроить. Ручные изменения Calendar не обязаны становиться правками дневника.

**[П]** Настройка интеграции показывает enabled/disabled, последний результат/ошибку и безопасный retry. Конкретные selectors календарей и набор sync controls определяются интеграционным этапом.

### Данные и обслуживание

**[Б]** Нужны переносимость, export/backup/restore semantics; при migration — явная операция, backup/snapshot, read-only maintenance, validation и report с возможностью выборочного before/after.

**[О]** Отдельные экраны экспорта/восстановления и migration comparison проектируются при реализации этих операций. Не включать фиктивные «Экспорт» и «Восстановить всё» в ранний интерфейс.

## 17. S12 — Входящие: дополнительный интерфейс [П]

Наличие capture pipeline и raw preservation подтверждено. Самостоятельный пользовательский Inbox screen в ближайшем web scope не подтверждён.

Если он включается, минимально полезный состав: source, время поступления, исходный текст/материалы, состояние обработки, созданные Entry, причина needs-review/ошибки. Открытие raw не означает его редактирование или уничтожение.

Действия: посмотреть источник, открыть полученную Entry, повторить failed processing безопасно. Неоднозначность даты/содержания требует явного review, а не выдумывания факта.

Не смешивать:

- исходное capture item, ещё не ставшее Entry;
- Entry с неопределёнными metadata;
- pending AI proposal для существующей Entry.

Старые file-workflow папки `new/processing/needs_review/failed` служат контекстом, но не являются автоматически утверждёнными названиями пользовательских вкладок.

| Routines → запуск / результат | Run flow / S10 | Routine и run ID; Draft исключаются |
| Revision/proposal → run details | S10 | AI run/result ID |
| Home / Entry Browser → + New Entry | S04/S05 | Сразу новый Entry ID и durable Draft |
| Expanded card → Compare | S04 compare mode | Base Revision слева, editable Draft справа |

**[П]** Deeplinks к Entry/revision/proposal не зависят от title/date/path rename. Если объект отсутствует или недоступен, показывается корректное состояние и возврат к дневнику.

## 19. Общие состояния, адаптивность и доступность

### 19.1 Обязательные состояния

| Ситуация | Требование |
|---|---|
| Загрузка | [П] Показать, что данные ещё загружаются, без ложного пустого результата |
| Нет записей / нет результатов | [П] Различать пустой дневник и пустую выборку; предложить сброс фильтров где уместно |
| Сеть/Drive недоступны | [Б] Видимая ошибка и safe retry; введённый текст не теряется |
| Commit не удался | [Б] Draft сохраняется; успех не объявляется |
| Потерян editing lease | [Б] Paused/read-only, уведомление, local recovery |
| Изменился current/base | [Б] Compatibility/conflict flow вместо overwrite |
| AI-модель недоступна | [Б] Нет silent fallback |
| Raw/external asset недоступен | [П] Сохранить видимость связи, показать недоступность; не подменять её отсутствием Asset |
| Migration maintenance | [Б] Запрет mutations; явный read-only status |
| Job закончен при закрытой странице | [Б] При открытии доступны результат и актуальный статус |

### 19.2 Адаптивность

**[Б]** Browse/read/search доступны на телефоне по этапам. EntryPanel адаптируется по контейнеру. Сложные comparison/debug функции могут сначала быть desktop-oriented.

**[П]** На телефоне основные действия не уходят за экран; теги переносятся, длинный текст читаем, dialog можно закрыть/подтвердить, gallery доступна swipe и кнопками. Если detail comparison ещё не поддержан, это указано явно, а данные/действия не изображаются работающими.

### 19.3 Доступность [П]

Клавиатурный доступ и видимый focus; подписи для icon-only actions; подтверждение destructive actions; не полагаться только на hover; состояния/дифф обозначаются также текстом/знаком, не одним цветом. После modal/review фокус возвращается к понятной точке. Точный визуальный стиль и tokens относятся к следующему design pass.

### 26.3. Уточнение 18.10.2026 — явные commit-действия

Принят первый вариант FQ-01: Save фиксирует ручной Draft; Apply подтверждённого AI proposal и Restore исторической версии самостоятельно создают новые Revision, без отдельного Save после них. Autosave/Return later/Discard/Reject Revision не создают. Restore из Trash относится к lifecycle и content Revision не создаёт. 18.10 также подтверждены прежние исключения: первая normalization из raw и existing tags по routine policy; подробности в §26.4.

### 26.4. Уточнение 18.10.2026 — AI auto-apply

Первая normalized Entry может создаваться автоматически из сохранённого raw с явной uncertainty; existing tags могут добавляться автоматически при высокой уверенности, если это разрешено routine policy. Изменение existing Entry создаёт новую committed Revision с trace routine/input/result; первая обработка создаёт первую committed Revision. Existing Entries с Draft пропускаются, ручной Draft AI не переписывает. Изменения текста existing Entry и создание новых тегов по умолчанию остаются proposals. Конкретные confidence thresholds не фиксируются.

В AI activity видны origin automatic, routine и input Revision, результат и созданная Revision; автоматически применённое изменение — исторический факт, не открытый proposal. FQ-01 закрыт; [история решения](04-open-questions.threads/04_PQ-004_raw-revisions-ux/01_FQ-01_revision-commit-actions/00_thread.md).


### 26.5. Уточнение 18.10.2026 — merge тегов

Merge — операция каталога: oldTagId разрешается в survivingTagId через mergedInto redirect. Current Entry/Draft, поиск и счётчики используют canonical ID с дедупликацией; snapshots committed Revision и существующие Draft физически не переписываются, новые content Revision ради merge не создаются. Операция фиксируется в audit каталога. Следующий обычный Save может записать surviving ID; отдельной массовой миграции Entry нет. Type/color survivor и перенос aliases сохраняют ранее принятые правила. Само объединение не помечает каждую Entry изменённой ради создания content Revision. Historical labels/rendering остаются отдельной policy.

**История:** [FQ-02](AI-Diary-Functional-Spec-v0.1.threads/01_FQ-02_tag-merge/00_thread.md).


### 26.6. Уточнение 18.10.2026 — потерянное подтверждение Save

Если подтверждение Save потеряно, приложение показывает «Проверяем сохранение» и после восстановления связи автоматически выясняет исход операции. При уже состоявшемся commit возвращается та же Revision; если commit не состоялся, безопасно повторяется та же операция с тем же operationId и зафиксированным snapshot. Повтор не создаёт дубликат и разрешён только при актуальных base/ownership checks, без отмены/замены операции. При conflict или потере права записи автоматический commit прекращается с понятным сообщением; введённые данные сохраняются. Неизвестный исход не выдаётся ни за успешное, ни за достоверно неуспешное сохранение.

При неизвестном исходе не показывать ошибку как доказательство отсутствия commit; статус «Проверяем сохранение» отличается от обычного Draft saved и подтверждённой Revision. 18.10 для первой версии выбрана временная блокировка editor и повторного Save до определения результата (§26.7). **История:** [FQ-03](AI-Diary-Functional-Spec-v0.1.threads/02_FQ-03_reliable-save/00_thread.md).


### 26.7. Уточнение 18.10.2026 — простой Save без параллельного ввода

В первой версии после начала Save редактируемые поля этой Entry и повторный Save временно блокируются до определения результата операции. Просмотр, прокрутка и копирование текста доступны. При потерянном подтверждении действует автоматическая проверка/безопасный retry той же операции, статус «Проверяем сохранение»; редактор остаётся read-only. После подтверждённого успеха редактор доступен с сохранённым состоянием. После достоверного отказа без commit и без конфликта блокировка снимается, исходный Draft сохраняется для исправления/повтора. Conflict или утрата lease разрешаются соответствующим flow; сохранённый текст не очищается и право записи самовольно не восстанавливается. Продолжение ввода параллельно неподтверждённому Save в первую версию не включается.

Это заменяет предложение разрешить дальнейший ввод до подтверждения Save; то предложение осталось только в истории обсуждения и не является требованием. Переходы/dirty guard по-прежнему должны сохранять Draft и актуальный статус выполняющейся операции. **История:** [FQ-03](AI-Diary-Functional-Spec-v0.1.threads/02_FQ-03_reliable-save/00_thread.md).


### 26.8. Уточнение 18.10.2026 — уникальные aliases

Один и тот же alias не может принадлежать двум самостоятельным активным canonical tags. Если alias уже занят, добавление его второму тегу отклоняется с указанием существующего тега; существующие теги автоматически не объединяются. Повторы aliases внутри одного canonical tag дедуплицируются. Merge redirect разрешается в survivor и не считается вторым самостоятельным владельцем alias.

Повтор одного alias у разных самостоятельных тегов не предлагается как пользовательский сценарий выбора между омонимами. Pending Create и editor каталога должны учитывать уникальность. Пересечения alias с canonical name другого активного тега также запрещены (§26.9); сравнение без учёта регистра принято (§26.11), резервирование обозначений удалённых тегов принято (§26.12), остальные правила Unicode/пробелов ещё обсуждаются. **История:** [FQ-04](AI-Diary-Functional-Spec-v0.1.threads/03_FQ-04_tag-aliases/00_thread.md).


### 26.9. Уточнение 18.10.2026 — единое пространство names/aliases

Canonical names и aliases образуют единое пространство уникальных обозначений между самостоятельными активными canonical tags. Нельзя создать отдельный тег с именем, уже занятым как name или alias другого тега, либо назначить ему такое имя/alias. При конфликте показывается существующий тег; запись дубликата отклоняется без автоматического merge, переноса обозначения или перепривязки Entry relations. Идея отдельного переноса имени/alias между тегами сохранена на будущее; в текущий scope такой сценарий не включён.

В текущем интерфейсе конфликта достаточно показать владельца обозначения; кнопки «Забрать имя»/«Перепривязать» не включаются. Существующие rename/alias editor и явный merge остаются со своими согласованными правилами; новый transfer workflow не добавляется. **История:** [FQ-04](AI-Diary-Functional-Spec-v0.1.threads/03_FQ-04_tag-aliases/00_thread.md).


### 26.10. Уточнение 18.10.2026 — #_name для снятого тега

При Save упоминания явно снятого через chip тега преобразуются из #name в #_name, включая употреблённые aliases, с сохранением написанного обозначения. Маркер #_name остаётся в тексте, чтобы такие места можно было найти Text search; он не является активным hashtag, не создаёт связь и не восстанавливает chip. Не считать #_name присутствующим активным упоминанием при нормализации linked tags; обычный Tag filter по-прежнему работает по tagId/relations. Преобразование затрагивает упоминания снятого тега, а не все символы # в документе; повторный Save не добавляет второй underscore. Если тег добавлен обратно до Save, его упоминания не помечаются как снятые. Дополнительный вопрос на каждом Save для этого преобразования не требуется.

В view/editor маркер показывается обычным текстом, доступным текстовому поиску, без активного tag styling. Tag autocomplete/Create не срабатывает на префикс #_. Менять весь текст или все # на основании одной снятой связи нельзя. **История:** [FQ-04](AI-Diary-Functional-Spec-v0.1.threads/03_FQ-04_tag-aliases/00_thread.md).

### 26.11. Уточнение 18.10.2026 — сравнение names/aliases без учёта регистра

Canonical names и aliases сравниваются без учёта регистра при проверке уникальности и lookup, включая autocomplete. Спорт, спорт и СПОРТ считаются одним обозначением; различие только в регистре не позволяет создать второй самостоятельный тег или занять его обозначение. Выбранное пользователем написание сохраняется для отображения, автоматическое приведение отображаемого текста к нижнему регистру не требуется. Это правило не меняет tagId и не переписывает существующий текст или immutable snapshots.

Проверка применяется в Create, Rename, alias editor и других путях изменения каталога; pending Create из Entry не позволяет обойти занятость обозначения другим регистром. При конфликте используется уже принятый показ существующего тега. Резервирование обозначений удалённых тегов принято (§26.12); остальные правила Unicode/пробелов пока открыты. **История:** [FQ-04](AI-Diary-Functional-Spec-v0.1.threads/03_FQ-04_tag-aliases/00_thread.md).

### 26.12. Уточнение 18.10.2026 — обозначения удалённых тегов

После soft delete тега его canonical name и aliases остаются занятыми за тем же tagId, в общем пространстве обозначений без учёта регистра. Нельзя создать другой тег или назначить ему name/alias, совпадающий с обозначением удалённого тега. При таком конфликте интерфейс показывает удалённый тег и предлагает явный Restore существующего тега вместо создания нового. Сам ввод имени не восстанавливает тег автоматически. До Restore сохраняется запрет новых links и исключение удалённого тега из обычных autocomplete/cloud; прежние tagId, relations и история сохраняются.

Проверка занятости учитывает удалённые теги в Create, Rename, alias editor и pending Create из Entry. Предложение Restore при конфликте не возвращает удалённый тег в обычные подсказки до подтверждённого восстановления. **История:** [FQ-04](AI-Diary-Functional-Spec-v0.1.threads/03_FQ-04_tag-aliases/00_thread.md).

### 26.13. Уточнение 18.10.2026 — формат дописываемых hashtags

При Save недостающие упоминания связанных тегов дописываются в конец body одной строкой, hashtags разделяются одним пробелом. От непустого текста эта строка отделяется пустой строкой; отдельного заголовка Tags: нет. Уже имеющиеся canonical/alias упоминания остаются на своих местах и не дублируются. Если все связанные теги уже упомянуты, новая строка не добавляется; повторный Save не создаёт повторный suffix. В пустом body добавляется только строка hashtags, без ведущей пустой строки. Маркер #_name не считается активным упоминанием.

**История:** [FQ-04](AI-Diary-Functional-Spec-v0.1.threads/03_FQ-04_tag-aliases/00_thread.md). Формат suffix согласован; технические правила Unicode/пробелов в обозначениях и грамматики распознавания mentions остаются открытыми.

### 26.15. Уточнение 18.10.2026 — вложения в Draft и доступность Save

Save недоступен, пока хотя бы одно оставленное вложение имеет неразрешённый статус: выбрано, загружается, проверяется, ошибка или требуется повторный выбор файла. Для продолжения нужно завершить загрузку/проверку, повторить её либо явно убрать вложение. Все оставленные attachments должны быть готовы к включению в Revision; для managed файла это подтверждённый original, для external — сохранённый валидный reference без обязательного скачивания original. Генерация thumbnail/preview не блокирует Save. До начала commit текст продолжает autosave в Draft.

Draft сохраняет весь состав вложений: связи с готовыми Asset, pending upload IDs, имена файлов, статусы и ссылки на durable upload/staging records. Успешно загруженные originals сохраняются в user-owned storage и остаются достижимыми из Draft до завершения Save или явного действия пользователя; уход со страницы и повторное открытие не должны терять вложения. Pending запись не исчезает при ошибке или перезапуске. Bytes, ещё не полученные хранилищем, не выдаются за durable: если продолжить upload автоматически нельзя, Draft сохраняет attachment intent и показывает «Выберите файл повторно». Удалять staging/original, на который ссылается актуальный Draft или незавершённая операция, нельзя.

Перед началом Save pending attachments остаются доступны для retry/повторного выбора/явного снятия, сам editor не блокируется одним фактом загрузки. После фактического запуска commit действует уже согласованный read-only editor. Причина disabled Save показывается рядом с вложением/кнопкой. **История:** [FQ-03/SQ-01](AI-Diary-Functional-Spec-v0.1.threads/02_FQ-03_reliable-save/01_SQ-01_upload-before-save/00_thread.md).

### 26.16. Уточнение 18.10.2026 — manual Save без изменения content

Manual Save, при котором итоговое сохраняемое content совпадает с текущей committed Revision, завершает эквивалентный Draft без новой Revision. Возвращается NO_CHANGE со ссылкой на существующую Revision; committedUpdatedAt и content History не меняются. Consume именно этого Draft и результат операции фиксируются durable с обычными ownership/base/idempotency checks. У новой Entry без Current первый успешный Save создаёт первую Revision. Согласованное создание Revision при Apply/Restore сохраняется.

Сравнение выполняется backend по итоговому content; UI dirty flag — только подсказка. В comparison входят Title/Text/EventTimeRange/Tag relations/Asset links; временные статусы autosave/загрузки и служебные timestamps не являются изменением content. Пробелы и регистр текста не игнорируются. Saved state показывается после durable NO_CHANGE outcome; при conflict Draft сохраняется. **История:** [FQ-03/SQ-02](AI-Diary-Functional-Spec-v0.1.threads/02_FQ-03_reliable-save/02_SQ-02_no-change-save/00_thread.md).

### 26.17. Уточнение 18.10.2026 — снятие единственной связи Asset

При снятии связи Asset с записью, в том числе при Discard добавлений Draft, применяется одно правило: если снимаемая связь единственная, предложить удалить сам Asset; если есть другие логические связи, снять только текущую без предложения глобального удаления в этом flow. Удаление — только по явному подтверждению и означает soft delete в Asset Trash, не permanent delete. При отказе от удаления связь всё равно снимается, Asset остаётся в библиотеке; при отсутствии Active Entry links он виден в Unlinked.

Проверяются логические потребители по разным entryId во всех lifecycle-состояниях, в других Draft и связанных незавершённых операциях; исторические references других Entries не теряются. Несколько Revision/Draft одной и той же Entry не считаются отдельными записями; historical link той же Entry сам по себе не запрещает предложить soft delete, поскольку история/links сохраняются. При Discard рассматриваются только связи, реально исчезающие относительно восстанавливаемой Current: Asset, остающийся в Current, не является кандидатом на удаление из-за Discard. Проверка актуальна перед выполнением; при новой чужой связи выполняется только unlink. Состояние Unlinked по Active-счётчику не используется как доказательство единственности. Незавершённая операция с неизвестным исходом сначала требует reconciliation.

При предложении удаления смысл двух вариантов явный: связь снимается в обоих случаях, Trash применяется только при подтверждении. Это уточняет прежний общий выбор unlink/delete у `×`; автоматический keep/Trash для всех новых uploads не принят. **История:** [FQ-08 — снятие связи / Discard](AI-Diary-Functional-Spec-v0.1.threads/04_FQ-08_discard-uploads/00_thread.md).

### 26.18. Уточнение 18.10.2026 — Restore Entry из корзины в активные

Restore Entry из Trash всегда возвращает запись в ACTIVE, независимо от того, была она Active или Archived перед удалением. Сохраняются тот же entryId, Current/content history и существующий durable Draft. Операция меняет lifecycle/audit и не создаёт content Revision; это не Restore исторической Revision.

После Restore строка Entry имеет состояние Active; повторная архивация доступна отдельным обычным действием. Восстановление из корзины не предлагает автоматический возврат в прежний архивный lifecycle. **История:** [FQ-08/SQ-01](AI-Diary-Functional-Spec-v0.1.threads/04_FQ-08_discard-uploads/01_SQ-01_restore-lifecycle/00_thread.md).

### 26.19. Уточнение 18.10.2026 — пересечение периода записи с фильтром

Фильтр по периоду включает интервальную Entry, если хотя бы часть её EventTimeRange пересекается с выбранным периодом; не требуется попадание начала или всего интервала внутрь фильтра. Например, поездка 1–10 июля видна при фильтре 5–7 июля. Одна Entry показывается один раз, независимо от количества пересекающихся дней. Это общее правило date filter; выбор календаря и связанные выборки используют ту же semantics при неизменном lifecycle scope.

Сценарий: «Поездка 1–10 июля» появляется при выборе 5–7 июля в Browser/календарном date filter. Точные включения граничных timestamp/date-only, timezone и отсутствующий To этим решением не определяются. **История:** [FQ-05 — пересечение периодов](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/00_thread.md).

### 26.20. Уточнение 18.10.2026 — Updated sort учитывает Draft

Сортировка «По изменению» учитывает последние содержательные правки Draft ещё до Save: при текущем Draft используется его content updatedAt, без Draft — committedUpdatedAt Entry. Это производный effectiveUpdatedAt для сортировки, а не изменение committed metadata и не новая Revision. Повторный autosave неизменного содержимого, heartbeat и технический progress загрузки не поднимают Entry заново. После Discard/NO_CHANGE без Draft используется прежний committedUpdatedAt.

Правка старой записи может поднять её при Updated desc до Save; при Updated asc используется тот же timestamp с обратным направлением. Новая Entry сортируется по timestamp Draft. Это не добавляет Draft отдельный приоритет, не меняет default Event date sort и не создаёт Revision. **История:** [FQ-06 — Updated sort](AI-Diary-Functional-Spec-v0.1.threads/06_FQ-06_updated-sort/00_thread.md).

### 26.21. Уточнение 18.10.2026 — архивные записи в рабочих очередях Home

Очереди «Черновики» / «Требует внимания» на Home включают ACTIVE и ARCHIVED Entries за всё время и исключают TRASH. Счётчик и список по клику используют одинаковые условия lifecycle и соответствующего признака; одна Entry считается один раз, независимо от числа review items.

Архивирование — отдельное явное действие «Архивировать» в меню записи. Автоматический перенос по возрасту не задан. Архив сохраняет запись, историю и имеющийся Draft; наличие Draft само по себе не запрещает архивацию. Home EntryList и TagCloud сохраняют свой ACTIVE scope. Scope Total entries и остальных статистических counters этим решением не определяется. **История:** [FQ-06/SQ-01](AI-Diary-Functional-Spec-v0.1.threads/06_FQ-06_updated-sort/01_SQ-01_home-queue-scope/00_thread.md).

### 26.24. Обсуждение 18.10.2026 — часовой пояс пользователя и время события

**[Д, 18.10.2026]** «Сегодня» и границы календарных rolling days Home определяются по сохранённому часовому поясу из настроек пользователя. При первоначальной настройке предлагается пояс устройства. Если обнаружено отличие пояса устройства от сохранённого пользовательского, приложение предлагает сменить настройку и применяет изменение только после подтверждения. Смена настройки может изменить текущее «сегодня» и период статистики, но не переписывает даты/время/timezone сохранённых событий и не переносит их между днями Calendar.

**[Д, ранее принято]** Entry сохраняет EventTimeRange с собственной timezone и точностью; date-only не превращается в фиктивное 00:00.

**[П, новая проработка]** Для события с точной датой и временем следует сохранять местные дату/время и timezone события и обеспечивать однозначное определение момента для сравнений и пересчёта. Физическая сериализация instant/offset и неоднозначности перевода часов ещё не утверждены. Пересчитанное время в пользовательской зоне — производное представление, не второй источник истины; UTC не требуется показывать обычному пользователю. Для date-only точный момент не придумывается.

**[Д, уточнение 18.10.2026]** Основное отображение Entry использует местные дату и время события в его сохранённом часовом поясе. При ручном создании пояс события по умолчанию берётся из настроек пользователя, если он там задан; иначе сохраняется прежний fallback на пояс устройства. Явно выбранный пояс события имеет приоритет над default. Пояс сохраняется в EventTimeRange записи; последующая смена пользовательских настроек не пересчитывает и не переписывает её местные дату/время или timezone. Если время суток отсутствует, оно не подставляется. Зона обозначается при отличии от пользовательской, чтобы время не читалось как пользовательское. UI вторичного пересчёта и необходимость его отдельного показа ещё не выбраны. **Обсуждения:** [настройка зоны](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/01_SQ-01_rolling-day-timezone/00_thread.md); [отображение события](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/02_SQ-02_event-time-display/00_thread.md).

### 26.25. Уточнение 18.10.2026 — основное время события и default timezone

Основное отображение Entry использует местные дату и время события в его сохранённом часовом поясе. При ручном создании пояс события по умолчанию берётся из настроек пользователя, если он там задан; иначе сохраняется прежний fallback на пояс устройства. Явно выбранный пояс события имеет приоритет над default. Пояс сохраняется в EventTimeRange записи; последующая смена пользовательских настроек не пересчитывает и не переписывает её местные дату/время или timezone. Если время суток отсутствует, оно не подставляется.

Например, ужин в Токио в 20:00 остаётся записью о 20:00 в Токио после возвращения пользователя домой. Точность date-only сохраняется. Смена default не является content edit существующей Entry и не создаёт её Revision. Для конкретной записи timezone остаётся редактируемым content по прежним правилам. **История:** [FQ-05/SQ-02](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/02_SQ-02_event-time-display/00_thread.md).

**[Д, уточнение 18.10.2026]** [Calendar и связанный date filter](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/03_SQ-03_calendar-event-date/00_thread.md) используют местные даты событий; подробности — §26.26. Настройка rolling days и предложение о смене пояса устройства согласованы в SQ-01 (§26.27).

### 26.26. Уточнение 18.10.2026 — Calendar по местным датам событий

Calendar относит Entry к местной дате события в сохранённой timezone самой записи. Событие «19 октября, 00:30, Токио» показывается на 19 октября, даже если в пользовательской timezone в этот момент ещё 18-е. Выбор дня/диапазона в Calendar открывает список с той же семантикой местных дат и принятым period overlap; индикатор и список используют одинаковый lifecycle scope. Смена пользовательской timezone не переносит сохранённые события между днями Calendar. Date-only сохраняется как дата без выдуманного времени.

Дневная выборка Calendar не должна сначала пересчитывать точные моменты всех событий в текущую timezone пользователя и тем самым менять их календарный день. Это не расширяет принятое правило на все фильтры с явно заданными часами: точные границы, mixed precision, DST и отсутствующий To по-прежнему требуют формализации. Источник «сегодня» для rolling counters согласован отдельно в [SQ-01](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/01_SQ-01_rolling-day-timezone/00_thread.md). **История:** [FQ-05/SQ-03](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/03_SQ-03_calendar-event-date/00_thread.md).

### 26.27. Уточнение 18.10.2026 — timezone пользователя для «сегодня»

«Сегодня» и границы календарных rolling days Home определяются по сохранённому часовому поясу из настроек пользователя. При первоначальной настройке предлагается пояс устройства. Если обнаружено отличие пояса устройства от сохранённого пользовательского, приложение предлагает сменить настройку и применяет изменение только после подтверждения. Смена настройки может изменить текущее «сегодня» и период статистики, но не переписывает даты/время/timezone сохранённых событий и не переносит их между днями Calendar.

Число и список по клику передают один и тот же выбранный календарный период. Настройка пользователя также служит default timezone ручной Entry по SQ-02; у сохранённой Entry своя timezone. Точное место поля настроек, вид и частота повторной подсказки ещё не выбраны. **История:** [FQ-05/SQ-01](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/01_SQ-01_rolling-day-timezone/00_thread.md).

Следующий выбор — [запись без окончания](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/04_SQ-04_missing-event-end/00_thread.md); принятое правило timezone не задаёт её длительность автоматически.

### 26.28. Уточнение 18.10.2026 — запись без окончания

Отсутствие To у Entry означает одиночное событие на указанную From дату/время, без автоматического продолжения до текущего дня или в будущее. Если указана только дата, дневной Calendar и связанный date filter относят запись к этой местной дате без выдуманного времени суток. Если задано время, опорой служит указанный момент без придуманной длительности. Это правило не меняет односторонние границы query filter.

Пример: запись «18 октября» без To видна на 18 октября и не появляется на последующих днях как продолжающееся событие. В редакторе To остаётся необязательным. Для интервала пользователь задаёт To; отдельная ongoing-функция этим решением не вводится. Точность date-only сохраняется; точные граничные и mixed-precision comparisons остаются отдельными вопросами. **История:** [FQ-05/SQ-04](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/04_SQ-04_missing-event-end/00_thread.md). Включение последнего дня date-only интервала согласовано отдельно в [SQ-05](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/05_SQ-05_date-only-end-inclusion/00_thread.md) (§26.29).

### 26.29. Уточнение 18.10.2026 — последний день date-only интервала включён

У интервала записи с From/To, заданными датами без времени, последний указанный день To включается целиком в пользовательском смысле. «Поездка 1–10 июля» видна и при выборе 10 июля. Date-only верхняя граница фильтра «по 10 июля» также включает весь указанный день. Сохранённые значения остаются date-only: фиктивные 00:00/23:59:59 в EventTimeRange не записываются.

Выбор 10 июля в Calendar и соответствующий date-only filter включают поездку 1–10 июля; при выборе 11 июля она не входит только из-за этой даты окончания. Число и список по клику согласованы. Явно заданные часы To, смешанная точность и DST этим решением не формализуются. **История:** [FQ-05/SQ-05](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/05_SQ-05_date-only-end-inclusion/00_thread.md). ### 26.30. Уточнение 18.10.2026 — date-only запись в фильтре по часам

Запись с известной датой, но без времени суток, включается в фильтр по часам того же дня как возможное совпадение. Например, «18 октября» без времени попадает в «18 октября, 12:00–14:00». В результате сохраняется явная пометка «время не указано»; запись не получает выдуманные часы, длительность на весь день или новое content-значение.

Пример ограничен одной timezone и внутренними часами дня; точные clock boundaries, смешанная точность двух границ, пересчёт между зонами и DST этим выбором не закрываются. Число и список по клику используют одну принятую семантику отбора. **История:** [FQ-05/SQ-06](AI-Diary-Functional-Spec-v0.1.threads/05_FQ-05_period-overlap/06_SQ-06_date-only-clock-filter/00_thread.md).

### 26.31. Уточнение 18.10.2026 — визуальная важность фоновой AI-работы

**[Д, направление UX пользователя]** Пока AI-обработка ожидает запланированного запуска, выполняется или ожидает автоматического продолжения/повтора, её состояние показывается менее заметно, чем причины, требующие действия пользователя. Scope очереди и счётчика позднее согласован в §26.32: фоновая работа сама по себе в них не входит.

**[Д, согласовано 18.10.2026]** Отображение различает следующие ситуации; конкретные цвета и layout остаются открытыми:

| Ситуация | Показ |
|---|---|
| Реально запланирован запуск / идёт обработка | Спокойный статус «Ожидает обработки» / «AI обрабатывает» |
| Временная ошибка; назначен автоматический повтор | Мягкое предупреждение «Повторим автоматически» |
| Продолжение требует действия пользователя | Более заметное «Требует внимания» с причиной и доступным действием |

Нормальная обработка не объявляется ошибкой только из-за ожидания. Предложение не задаёт новые гарантии автоповтора, сроки, лимиты попыток или точную палитру. Статус показывает фактическое состояние job; техническая retry-policy остаётся отдельным проектом. Если у Entry уже есть другая причина внимания, например открытый proposal или conflict, наличие фоновой работы не скрывает её.

**[Д, 18.10.2026]** В очередь и счётчик включаются только причины, требующие пользователя; queued/running/автоматический retry сами по себе туда не добавляются. **История:** [FQ-06/SQ-04](AI-Diary-Functional-Spec-v0.1.threads/06_FQ-06_updated-sort/04_SQ-04_failed-ai-attention/00_thread.md).

### 26.32. Уточнение 18.10.2026 — Needs attention требует пользователя

В очередь, фильтр и счётчик «Требует внимания» входят только актуальные причины, требующие действия пользователя, в том числе ошибка AI-обработки, после которой без пользователя продолжить нельзя. Ожидание запланированного запуска, выполняющаяся обработка и назначенный автоматический повтор сами по себе не добавляют Entry в Needs attention: они показываются спокойным статусом, а временная ошибка с автоповтором — мягким предупреждением. Независимые причины внимания, например открытый proposal или conflict, при этом сохраняются. Одна Entry считается один раз; старый уже разрешённый failed run сам по себе причиной не является.

Home очередь сохраняет ранее принятый ACTIVE + ARCHIVED scope без TRASH; число и список по клику используют одинаковые условия. Мягкий статус фоновой работы не приглушает независимую причину внимания той же Entry. Детали retry, разрешения ошибок и audit schema не утверждаются этим продуктовым выбором. **История:** [FQ-06/SQ-04](AI-Diary-Functional-Spec-v0.1.threads/06_FQ-06_updated-sort/04_SQ-04_failed-ai-attention/00_thread.md).

### 26.33. Уточнение 18.10.2026 — убрать конкретную ошибку AI из внимания

Пользователь может явно убрать из «Требует внимания» конкретную причину ошибки AI без успешного повторного запуска, если обработка больше не нужна. Снимается только эта причина; неуспешный Run и его история сохраняются и не помечаются успешными. Другие причины внимания Entry остаются; при отсутствии остальных причин Entry выходит из очереди и счётчика. Новая ошибка нового запуска может снова потребовать внимания и не наследует снятие прежней. Действие не удаляет Entry/историю, не создаёт content Revision, не выключает routine глобально и не отменяет выполняющийся job.

UI предоставляет явное действие у конкретной ошибки; рабочее название — «Убрать из внимания». Это не общий сброс всех review items Entry. Точное место кнопки и physical resolution/audit schema остаются деталями реализации. **История:** [FQ-06/SQ-05](AI-Diary-Functional-Spec-v0.1.threads/06_FQ-06_updated-sort/05_SQ-05_dismiss-ai-error/00_thread.md).

### 26.34. Уточнение 18.10.2026 — трёхпанельный review и «Принято частично»

Подробный review использует три панели: исходник Base — сохранённое состояние, на котором работал AI, только чтение; Result — редактируемый будущий итог; Proposal — исходное предложение AI, только чтение. В Result и Proposal подсвечиваются изменения относительно Base. Если пользователь принимает только часть предложения и подтверждает итоговый Result, proposal получает понятный статус «Принято частично» и закрывается целиком как разобранный. Создаётся одна committed Revision с подтверждённым Result, без дополнительного Save. Исходный Proposal и итоговый Result/Revision сохраняются в AI history; непринятые части не остаются pending и автоматически не превращаются в новые proposals. Причина внимания этого proposal снимается, остальные причины Entry сохраняются.

Base не подменяется текущей пользовательской настройкой или новой Current Revision: это исходное состояние run/proposal. При изменившемся Current подробный review учитывает совместимые изменения и даёт разрешить conflicts; перед Apply обязательны повторные ownership/base checks. Подсветка не отменяет возможность ручного редактирования Result. Точный diff algorithm, цвета, storage outcome enum и способ трассировки принятых/непринятых фрагментов — техническая конкретизация. **История:** [FQ-07](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/00_thread.md).

### 26.35. Уточнение 18.10.2026 — черновик разбора AI review

Незавершённый Result подробного AI review автоматически сохраняется как черновик разбора и восстанавливается после выхода, reload и следующего сеанса — по тому же принципу, что Draft записи. Пока Apply не подтверждён, исходный proposal остаётся pending, Current Entry и committed History не меняются. При возвращении ручные правки Result сохраняются; если Current изменился, выполняется обычная проверка base/current и разрешение conflicts без silent overwrite. Черновик разбора не подменяет существующий WorkingDraft ручного редактирования.

Для ухода с неприменёнными изменениями действует тот же принцип явного выбора, что и у Entry: применить Result, отбросить правки разбора либо вернуться позже с сохранённым прогрессом. Apply создаёт Revision по общему контракту; autosave черновика разбора этого не делает. Отбрасывание только правок Result не равно Reject исходного proposal. Состояние «черновик сохранён» показывается после подтверждения сохранности; несинхронизированные локальные правки не выдаются за durable. Ошибки сохранения и conflict не должны очищать введённый Result.

Точные пути/schema и recovery/concurrency контракт черновика разбора требуют технической конкретизации; общие lease/base/mutation guards сохраняются. **История:** [FQ-07/SQ-01](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/01_SQ-01_review-draft-resume/00_thread.md). Обычный повтор AI после ошибки без успешного результата согласован отдельно в [SQ-02](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/02_SQ-02_failed-run-retry/00_thread.md) (§26.36).

### 26.36. Уточнение 18.10.2026 — обычный повтор после ошибки AI

Достоверно failed AI Run без успешного результата не считается успешно already processed. Обычный повтор той же routineVersion/input Revision разрешён даже без изменения записи; обычный batch не пропускает запись только из-за такого failure. Неуспешный Run остаётся в истории. Для успешно выполненной обработки прежние already-processed правила сохраняются независимо от принятия/отклонения proposal; сознательный повтор успешной обработки использует Force rerun. Это правило не разрешает слепой повтор при неизвестном исходе и не меняет пользовательскую политику платных автоматических AI retries.

Ручное «Повторить» не требует менять Entry или обходить already-processed через Force rerun только из-за достоверного failure. Queued/running работа не дублируется; uncertain outcome сначала проверяется по прежним recovery правилам. Платная retry-policy и её default экономии взяты из [AQ-OPS-002](04-open-questions.threads/37_AQ-OPS-002_safe-retries/00_thread.md); отсутствие already-processed block не означает автоматического согласия на новый платный вызов. Точные operation/attempt IDs и limits/backoff — техническая конкретизация. **История:** [FQ-07/SQ-02](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/02_SQ-02_failed-run-retry/00_thread.md).

### 26.37. Уточнение 18.10.2026 — отмена batch сохраняет готовую часть

При отмене пакетной AI-обработки сохраняются уже успешно опубликованные результаты: pending proposals и разрешённые routine policy committed изменения. Оставшаяся работа останавливается по общему cancellation contract; отмена не выполняет массовый Undo/Reject уже готовых результатов. Pending proposal не становится применённым от сохранения после отмены. Отменённый job не получает право позднего commit; история batch различает завершённую и отменённую/неисполненную части.

Пример: из 20 Entries для 7 уже готовы результаты; после отмены эти 7 результатов доступны, оставшаяся работа останавливается. Уже опубликованные auto-apply изменения не откатываются; готовые proposals остаются доступными для review. Работа, не завершённая до cancellation guard, не получает право позднего применения ответа AI. Точное разрешение гонки commit/cancel, provider cancellation и schema batch outcomes — техническая конкретизация. **История:** [FQ-07/SQ-03](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/03_SQ-03_batch-cancel-results/00_thread.md).

**[Д, 18.10.2026]** [Обычный повтор отменённой/необработанной части](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/04_SQ-04_interrupted-batch-retry/00_thread.md) разрешён; готовая часть пропускается, полный повтор доступен отдельным явным действием (§26.38). Текущая отмена сама по себе не возобновляет batch.

### 26.38. Уточнение 18.10.2026 — продолжение и полный повтор batch

После подтверждённой отмены пользователь может обычным повтором обработать отменённую/необработанную часть без успешного результата. Для того же выбранного набора и неизменных routineVersion/input Revision уже успешно обработанная часть пропускается; отмена без результата сама по себе не означает already processed. Сознательный полный повтор выбранного набора, включая уже успешную часть, доступен отдельным явным действием Force rerun. Общие eligibility/Draft/ownership checks сохраняются; прежняя queued/running работа не дублируется, неизвестный исход сначала требует reconciliation. История предыдущих запусков сохраняется.

Пример: для выбранных 20 Entries семь уже готовы. Обычное продолжение обрабатывает оставшиеся 13 при соблюдении eligibility; явный полный повтор заново обрабатывает весь выбранный набор по общим AI policy. Это разные намерения пользователя, и интерфейс должен различать их явно.

**[П, короткие названия 18.10.2026]** Для этих двух действий предлагаются «Продолжить» и «Повторить всё». Число записей/контекст выбранного набора показываются рядом с действиями, чтобы «всё» не читалось как весь дневник. Короткие формулировки ещё обсуждаются; пользователь согласовал поведение, но попросил подумать над названиями.

Рабочие длинные пояснения можно оставить рядом/в описании: продолжение — «только необработанные», полный повтор — «включая уже обработанные». Точный layout и источник набора при повторе через новый filter vs исходный snapshot не выбираются этой правкой. **История:** [FQ-07/SQ-04](AI-Diary-Functional-Spec-v0.1.threads/07_FQ-07_partial-proposal/04_SQ-04_interrupted-batch-retry/00_thread.md).
