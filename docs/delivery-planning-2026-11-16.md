# AI Diary — рабочие договорённости о задачах, оркестрации и раннем деплое

**Дата обсуждения:** 2026-11-16  
**Статус:** рабочие заметки для согласования Product Owner; не заменяют принятый baseline или архитектурные решения  
**Связанные документы:** [живой план](plan.md), [web/API roadmap](implementation-plan-web-mvp.md), [архитектура](architecture.md), [правила агентской команды](agent-team/README.md), [оркестрация](agent-team/orchestration/README.md), [формат задач](agent-team/tasks/README.md).

> Цель: обеспечить максимально ранний проверяемый пользовательский результат без потери данных и при этом постепенно перейти от ручной работы Claude/Codex к контролируемому облачному исполнению.

## 1. Что уже определено в действующих документах

- **Продукт:** приоритет web/API MVP; frontend — React + TypeScript + Vite, backend — Kotlin/Ktor; canonical diary content в пользовательских файлах (сначала Google Drive). Не возвращаться к устаревшему Firebase Data Connect / Android-first документу как к текущему утверждённому плану без отдельного архитектурного решения.
- **Runtime backend:** Google Cloud Run Service; фоновые run-to-completion операции — Cloud Run Jobs, расписания — Cloud Scheduler. Первоначально одно развёрнутое окружение, без обязательного постоянно работающего staging.
- **CI/CD продукта:** проверки PR — автоматические; deploy backend/web — по ручному разрешению, с rollback и секретами вне Git. Конкретные команды деплоя ещё должны соответствовать фактическому коду.
- **Frontend hosting:** **WEB-008 остаётся открытым**: тот же Cloud Run или статический Google hosting; Cloudflare Pages/Firebase Hosting можно дополнительно оценить, но нельзя объявлять выбор сделанным.
- **Cloudflare Pages сейчас:** отдельная публикация безопасных синтетических презентаций результатов агентов, а не хостинг приложения AI Diary: [публикация](agent-team/publishing/README.md).
- **Задачи агентов:** канонические `TASK-NNNN_slug/task.md` и история в репозитории; GitHub Issues/PR — интерфейс и транспорт, не единственный источник истины. Существующие категории — `tasks/active/` и `tasks/completed/`. В `active` пока входят и черновики.
- **Безопасность исполнения:** no auto-merge/deploy; Claude/Codex и тесты не работают с живыми данными дневника, Abacus и реальными Google API без отдельного разрешения. Ревью независимое, максимум два цикла автоматических исправлений.

## 2. Принципы для будущей нарезки требований на задачи (предложение)

1. **В первую очередь — время до следующего работающего сценария (walking skeleton / vertical slices).** Раскладывать требования так, чтобы можно было рано открыть сайт на телефоне, увидеть запись и проверить конкретное поведение. Не строить все горизонтальные слои до первой демонстрации.
2. **Каждый срез имеет проверяемый пользовательский результат и план деплоя.** Ранние демонстрации допускаются на синтетических данных; интеграция с реальным дневником и особенно запись в него — только после надёжного Save/recovery, проверки Google OAuth/секретов и отдельных разрешений.
3. **Прогрессивное усложнение.** Сначала минимальное, но сквозное поведение; затем editor/search/tag proposals/AI. Отмечать, какие требования отложены или заменены безопасной заглушкой, и не выдавать заглушку за реализованный продукт.
4. **Traceability.** Для каждой задачи сохранять ссылки на исходные requirement IDs/threads, зависимости, acceptance criteria, Documentation Impact, этап (P*/E*), предполагаемую демонстрацию и необходимый тест.
5. **Сначала проект бэклога, потом массовая регистрация.** Claude и ChatGPT предлагают разбиение, последовательность и зависимости; Product Owner проверяет план. Не создавать сотни `TASK-*` и GitHub Issues автоматически до проверки. Номера TASK назначает только единый регистратор после его принятия.
6. **Не жертвовать инвариантами:** preservation of raw inputs, idempotency, recovery, отсутствие потери пользовательских правок и безопасный откат — обязательные условия релизов с реальными данными.

**Предлагаемые ранние демонстрации, не утверждённые сроки:** (а) доступный по HTTPS минимальный макет/каркас на синтетике; (б) тестовый путь Calendar Inbox → Entry → Timeline (P2); (в) read-only web E0 со списком/просмотром; (г) первая безопасная лёгкая правка с ревизиями; (д) AI-предложения тегов. Уточнить порядок при нарезке, не обещать реальный доступ к записям на этапе (а).

## 3. Бэклог и принятие задач в работу (предложение к изменению протокола)

- Рассмотреть добавление `tasks/backlog/` наряду с существующими `active/` и `completed/`. **Такой папки и поддержки её регистратором пока нет.** Нужно решить, являются ли backlog/active физическими папками, а `draft/ready/implementing/reviewing` — полем статуса, чтобы не смешивать категории и состояние.
- Приоритет крупных этапов и разрешение на запуск утверждает Product Owner. Внутри **явно разрешённой группы задач** оркестратор сможет выбирать следующую по зависимостям, приоритету, ресурсам и статусу; не должен запускать каждый draft автоматически.
- Начальный лимит параллелизма как рабочее предложение: одна задача в реализации и одна в независимом review. Обязательны остановка на `needs-human/blocked`, расходные лимиты, безопасные повторы и отчёт о выборе следующей задачи.
- GitHub Issues и при необходимости GitHub Projects — удобная доска и уведомления. Каноническое подробное описание остаётся в `task.md`; нельзя полагаться только на текст Issue.

## 4. Пользовательский сценарий управления агентами (целевое состояние, не реализовано)

1. Product Owner обсуждает с ChatGPT голосом статус или новую идею.
2. ChatGPT формирует предложенную задачу/критерии; по разрешению запускает регистрацию через GitHub API → GitHub Actions `workflow_dispatch` → центральный Python-регистратор → commit `task.md`/реестра.
3. Регистрация создаёт **только draft**. Отдельное разрешение/утверждённый пул задач переводит задачу в исполнимое состояние.
4. Оркестратор dispatch-ит Claude Code Cloud, получает PR, передаёт исходные критерии и diff в Codex Cloud, проверяет CI, при необходимости возвращает замечания Claude (не более двух циклов).
5. Готовый результат и презентация передаются Product Owner. Без принятия нет auto-merge и deploy.

**Что реально существует на дату заметки:** [PR #14](https://github.com/mamton76/ai-diary/pull/14) — draft первого этапа: registrar `registry.json`, `register_task.py` и ручной `workflow_dispatch`, ещё не в master и без автоматической передачи полного текста разговора. Адаптеры cloud Claude/Codex, событийный маршрутизатор, связь голосового чата с запуском Action, очередь и затраты остаются работой TASK-0003. [PR #13](https://github.com/mamton76/ai-diary/pull/13) — отдельный draft review file format/Save и вопросы к Product Owner. Не считать эти PR слитыми или их функциональность уже работающей.

## 5. Хостинг: что решить отдельно

**Cloudflare Pages** технически подходит для статического React/Vite frontend, а **Firebase Hosting** также возможен как кандидат; это **не означает** перенос Kotlin/Ktor API или canonical Google Drive storage с согласованной архитектуры. Firebase был в более ранних проектных материалах; текущие source-документы репозитория уже выбрали Cloud Run для backend и оставили WEB-008 для web hosting.

До утверждения WEB-008 сравнить Cloudflare Pages, Firebase Hosting, статический Google hosting и размещение UI вместе с Cloud Run по:
- безопасной связке с Cloud Run API и Google login/OAuth (cookies, CORS, домены);
- защите личных данных и отсутствию публичных preview с реальным содержимым;
- стоимости и простоте deploy/rollback/preview;
- сложности обслуживания и возможности раннего прототипа.

Решение о frontend hosting вынести в соответствующий canonical thread/архитектурный документ. Эту заметку не трактовать как финальный выбор.
