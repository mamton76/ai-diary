# Orchestration — текущий протокол

**Версия:** v0.1 proposal. Описывает ожидаемую машину состояний; **реальный облачный оркестратор ещё не развёрнут**.

## Источники и интеграции

- Канонический task record — docs/agent-team/tasks/{active,completed}/TASK-NNNN_slug/.
- GitHub Issue/PR — внешние зеркала и транспорт событий. Их номера, статусы и комментарии можно хранить ссылками, но не использовать как единственный идентификатор или единственную историю.
- Адаптер обязан переживать повторную доставку событий: каждый переход идемпотентен по (task ID, transition, source revision/event id). Избегать рекурсивного срабатывания ботов.
- Облачные Claude/Codex запускаются адаптерами после проверки разрешений/авторизации; провайдерские API и учётные лимиты устанавливаются отдельной реализационной задачей.
- Контент задачи переносим: Markdown-файлы должны быть понятны без GitHub. Машинный state/cache и run logs могут храниться отдельно, если это не единственная существенная копия информации.

## Состояния

| State | Смысл | Следующий шаг |
|---|---|---|
| draft | Формулируется задача, ещё не разрешён запуск | ready после явного согласования |
| ready | Входы, границы и критерии определены | planning / implementing |
| planning | План и Documentation Impact проверяются | implementing или needs-human |
| implementing | Исполнитель меняет код и документацию | reviewing |
| reviewing | Независимый review + CI + документация | implementing, blocked либо ready-for-human |
| blocked | Ошибка/зависимость, которую автоматика не разрешит | ready / implementing после решения |
| needs-human | Нужен выбор по существенному вопросу | возврат в работу после решения |
| ready-for-human | Критерии выполнены, PR и сводка готовы | completed после принятия и разрешённых действий |
| completed | Результат принят, финальные файлы и ссылки сохранены | архив, не мутировать молча |

Возврат в implementing из reviewing допустим не более **двух автоматических циклов**. Блокирующие замечания/провал CI не скрываются за положительной LLM-оценкой.

## Минимальный цикл

1. Из разговора или плана формируется переносимый task.md, затем при необходимости GitHub Issue с обратной ссылкой. **Создание Issue само по себе не запускает выполнение.**
2. Только явный статус ready и разрешения инициируют облачную сессию Planner/Developer.
3. Developer работает в изолированной ветке и отдаёт commit/diff, test logs и изменения документации.
4. Reviewer получает **оригинальную постановку и diff** и выдаёт аргументированное review. CI исполняется независимо.
5. Orchestrator собирает результаты, передаёт замечания, ограничивает циклы и расход ресурсов.
6. По прохождении Definition of Done формируются result.md, discussion/00_all.md, итоговая сводка и PR.
7. После принятия пользователем, допустимого merge и финальной проверки документы задачи переносятся в completed/. **PR открыт ≠ задача completed.**

## Definition of Done (обязательный gate)

- Acceptance criteria выполнены и представлены проверяемые доказательства.
- Проверки/сборка/тесты прошли или явно документированы непройденные проверки и задача не объявлена готовой.
- Независимое ревью завершено, блокирующих замечаний нет.
- Documentation Impact был определён в task.md; актуальные документы изменены **вместе с кодом**, либо мотивированно указано «none».
- Отдельно сверены **ожидаемое поведение, текущее состояние реализации и история решений**. Принятые требования не подгоняются под реализацию.
- Все существенные решения, возражения, тестовые свидетельства и ссылки отражены в переносимой папке задачи.
- Не осталось блокирующих вопросов; опасные действия не выполнялись без разрешения.
- После согласования результата завершение зафиксировано в result.md, задача перемещена в completed/, связанные внешние статусы синхронизированы.

## Документация в каждой задаче

**Планирование:** найти impacted docs, разделить specification / implementation status / history, записать Documentation Impact в task.md.

**Реализация:** изменить соответствующие source docs в том же PR. Если реальность расходится с требованиями, инициировать canonical discussion thread, а не менять baseline молча.

**Ревью:** проверить не только код, но и все заявленные docs; отсутствие изменений должно быть объяснено.

**Завершение:** проверить ссылки, актуальный статус плана реализации, подтверждённые решения и полноту summary.

## Failure recovery и контроль

- Хранить task ID, текущий state, run ID, входной ref, выходной commit/PR, время, результат проверок и ограничение попыток.
- Повтор после таймаута сначала сверяет, был ли опубликован результат, а не начинает запись заново.
- Неполные и неоднозначные результаты → blocked, без автоматического merge.
- Ограничить попытки, время, токены/расходы, конкуренцию и доступ к внешним сервисам; логировать безопасно, без сырых пользовательских данных.

## Не реализовано в этом PR

Адаптеры Claude Cloud/Codex Cloud, event router, статусная синхронизация Issue ↔ файлы, durable queue, облачное выполнение и полная CI-цепочка. Это будущие задачи, а не возможности существующего скрипта конкатенации.
