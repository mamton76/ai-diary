### B. Пробелы формата — объекты, принятые после 18.10, которых нет в 07 и в схеме

1. **CaptureItem (CAP-013, этап E0)** — фундамент P1 по плану, но в формате только строка «inbox/…». Нет записи CaptureItem, raw receipt, состояния обработки и ключа идемпотентности (то же в ревью 08.11, H15).
2. **Происхождение записи (AI-19)** — «пользовательская / синтетическая с типом». В Entry state и в `revision.origin` его нет, а синтетический дайджест появляется уже с минимальным дайджестом (параллельно E0).
3. **Трекеры и журнал событий (AQ-AI-010, AI-036, этап E4)** — canonical-данные с provenance и версиями трекера; в формате их нет.
4. **Дайджест-proposal**: статус «Устарел» и напоминания (AQ-AI-011/SQ-02) не отражены в Proposal.
5. **Схема**: `publication.kind` содержит только BOOTSTRAP / REGISTER / SAVE / CONTROL; нет APPLY / RESTORE / LIFECYCLE / EXTERNAL_FILE_CHANGE (ревью 08.11, M13). Нет `$defs` для Asset, Proposal, Run, CaptureItem, Tracker.

### C. Существенный технический риск — автосохранение через общую цепочку публикаций

По 07 §5.1 каждый автосейв Draft меняет `draftRef` в Entry state, а Entry state меняется только публикацией в **общей** цепочке `_system/commits`. Значит, каждый сброс автосейва — это отдельный create файла в Drive, сериализованный со всеми остальными изменениями дневника. Следствия:
- тысячи мелких commit-файлов в год (автосейв, Register и Save на каждое сохранение);
- задержка Drive API на каждом автосейве и конкуренция за следующий slot между разными записями;
- холодный старт перечитывает цепочку с genesis; checkpoint описан только как кеш, политики сжатия нет.

Предложение (техническое, проверяется spike'ом и метриками OPS-008): вынести автосейв Draft в **собственную цепочку слотов записи** внутри `entries/<entryId>/draft/`, а в общую цепочку публиковать только Save, Apply, Restore, каталог, lifecycle и операции. Save ссылается на конкретную версию Draft и «потребляет» её в общей публикации, как сейчас. Добавить canonical checkpoint (снимок resource map каждые N публикаций) с правилом проверки, чтобы холодный старт не перечитывал всю историю.

### D. Вопросы Product Owner — влияют на то, как дневник выглядит в Drive

1. **Раскладка папок записей.** Сейчас `entries/<entryId>/` — плоский список непрозрачных ID, в Drive по нему ничего не найти глазами. Альтернативы: папки по дате создания `entries/2026/11/<entryId>/` (стабильны, не переносятся) или по дате события (удобнее, но перенос при исправлении даты).
2. **Читаемость `entry.md` без приложения.** Сейчас в нём только текст; заголовок, дата и теги — в JSON. Вариант: в удобную копию `entry.md` добавлять шапку (заголовок, дата, теги). Это materialized view, источник истины не дублируется.
