# Задачи команды — переносимый реестр

## Структура

Папка задачи: **TASK-NNNN_short-description**, где NNNN — стабильный четырёхзначный порядковый номер, short-description — короткий английский kebab-case slug (желательно 3–5 слов). Полный заголовок может быть по-русски внутри task.md.

- **active/** — задачи от draft до ready-for-human.
- **completed/** — принятые завершённые задачи, включая task.md, discussion и result.md.
- Папка не переименовывается при переносе между active и completed; ID не зависит от GitHub Issue/PR.
- Ссылки на Issue/PR хранятся в task.md/result.md, но отсутствие GitHub не должно мешать читать задачу.

В каждой задаче:

    TASK-0001_agent-team-protocol/
      task.md
      discussion/
        00_all.md              # generated, не редактировать
        threads/
          01_topic.md          # canonical
          02_other-topic.md
      result.md
      presentation/             # для небанальных задач; переносимый отчёт-презентация
        index.html              # предпочтительный формат, когда полезна интерактивность

**discussion/threads/** содержит отдельные смысловые треды; **discussion/00_all.md** — детерминированная конкатенация в лексикографическом порядке файлов. Источником истины остаются отдельные треды. Использовать:

    python3 scripts/agent-team/build_discussions.py --write
    python3 scripts/agent-team/build_discussions.py --check

Файл собирается с указанием исходных имён тредов; нельзя редактировать его отдельно. Если discussion для задачи отсутствует, не создавать пустые треды ради шаблона.

## Презентация результата для пользователя

Для **небанальной задачи** итоговым deliverable наряду с `result.md` является человекочитаемая презентация. Это не замена документальному отчёту, а удобный интерфейс приёмки.

Небанальной обычно считается задача, меняющая пользовательское поведение/UX, архитектуру или интеграцию, включающая заметные технические компромиссы, существенную диагностику либо несколько связанных результатов. Мелкие правки, форматирование и однозначные одношаговые исправления могут иметь только `result.md`. Для каждой задачи в `task.md` явно указать **Presentation: required / not-needed**; при `not-needed` написать причину. Пользователь может запросить презентацию для любой задачи.

- Формат выбирается по предмету задачи: **самодостаточный адаптивный `presentation/index.html`** — предпочтительно, когда важны визуальный обзор, сравнение и интерактивный сценарий. Допускаются Markdown, PDF или другие переносимые файлы в `presentation/`, если они понятнее.
- Презентация показывает **цель, до/после, что реально сделано, демонстрацию/сценарий, решения и компромиссы, проверки с доказательствами, обновлённую документацию, известные ограничения и то, что требуется решить пользователю**. Для технической задачи «до/после» может быть схема workflow, таблица поведения или воспроизводимый пример вместо скриншота UI.
- Интерактивность используется по делу: переключение до/после, просмотр сценариев, раскрывающиеся архитектурные решения, тесты и ссылки на исходники; декоративную интерактивность не навязывать.
- Нельзя выдумывать скриншоты, проценты, результаты тестов и демонстрировать нереализованный функционал как готовый. Симуляцию или mock отмечать явно.
- HTML должен открываться локально без сервера и сторонних CDN, быть удобен на телефоне и компьютере; никаких секретов, реальных diary data или небезопасного внешнего контента. Публикация в GitHub Pages и иных публичных местах **не автоматическая**, только отдельно разрешённая.
- `result.md` содержит ссылку на презентацию, исходный commit и список проверок. Ревьюер проверяет факты, безопасность, доступность и работоспособность навигации/интерактивных элементов. Для задач с `Presentation: required` отсутствие презентации блокирует состояние `ready-for-human`.

## Выдача ID и конфликты

Перед созданием задачи искать максимальный номер в **active/** и **completed/**; выбрать следующий. Если два агента одновременно создают один ID, второй PR должен разрешить конфликт и получить новый ID **до merge**. Не считать GitHub Issue number источником ID. В первой версии задачи создаются последовательно; параллельное резервирование ID требует отдельного механизма и проверки гонок.

## Lifecycle и документы

Новые задачи стартуют в active/, поле Status в task.md отражает актуальное состояние. Перенос в completed/ только после прохождения gates и принятия результата. Завершённую задачу не переписывать для следующей работы: создать новую с ссылкой на предыдущую. Технические изменения внутри одной задачи можно версионировать Git history.

При планировании указывать Documentation Impact. В result.md — фактические проверки и актуализированные source docs. Если необходим спорный продуктовый/архитектурный выбор, использовать существующий [discussion-threads skill](../../../skills/discussion-threads/SKILL.md); локальный task thread не должен подменять canonical product decision.
