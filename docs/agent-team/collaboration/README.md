# Collaboration — действующие правила команды

**Версия:** v0.1 proposal. Этот файл содержит **только актуальные предлагаемые правила**; основания и прежние варианты — в decisions/ и задачах.

## Роли

- **Product Owner (пользователь):** формулирует цель, утверждает существенные продуктовые/архитектурные изменения, решает разногласия агентов, разрешает merge/deploy.
- **Planner / Architect (Claude либо Codex):** изучает задачу и канонические источники, формирует план, acceptance criteria, Documentation Impact и явные неопределённости.
- **Developer (обычно Claude Code Cloud):** меняет код и документацию в собственной ветке/среде, пишет тесты, предоставляет diff и логи проверок.
- **Independent Reviewer (обычно Codex Cloud):** получает исходные критерии и diff, а не только самоотчёт разработчика; проверяет код, тесты, архитектуру и документацию.
- **QA (роль, не обязательный отдельный агент):** сверяет проверяемые критерии с реальными результатами CI/тестов.
- **Orchestrator (детерминированная автоматика):** запускает роли, контролирует статусы, расходы, попытки, права и передачу артефактов; не подменяет собой продуктовые решения.

Роли могут меняться. Автор кода не утверждает собственный независимый review.

## Общение и разрешение разногласий

1. Каждая передача задачи включает её ID, исходный commit/ref, цель, ссылки на канонические требования, критерии готовности, режим доступа и ожидаемый ответ.
2. Агент фиксирует доказуемые замечания: важность, путь/строка, воспроизведение, рекомендация. Отсутствие замечаний не приравнивается к успешной сборке.
3. Ревьюер может запросить исправление; оркестратор передаёт его разработчику. Максимум **две итерации** автоматического исправления и повторного ревью.
4. Если остаются блокирующие ошибки, разногласие или неопределённое требование, задача переходит в blocked / needs-human; не «согласовывать» позиции за пользователя.
5. Технические обсуждения, имеющие длительную ценность, сохранять в discussion/threads/ текущей задачи. Решения, меняющие продуктовый baseline, вести также через существующие canonical discussion threads по правилам skills/discussion-threads/SKILL.md.
6. Не создавать второй canonical thread по уже обсуждаемому вопросу. В задаче оставить ссылку и только собственный контекст исполнения.
7. Для пользователя готовить краткое текущее/итоговое summary: сделано, проверено, что спорно, что нужно решить; сохранять ссылки на подробные треды, PR и артефакты.
8. Для **небанальной задачи** до приёмки готовить отдельную **презентацию результата**: наглядное объяснение, что изменилось, при возможности интерактивный HTML с демонстрацией на безопасных синтетических данных. Исполнитель формирует материалы, независимый reviewer проверяет факты и работоспособность, оркестратор предоставляет ссылку пользователю. Не путать презентацию с доказательством прохождения тестов и не подменять её голословной похвалой выполненной работе.

## Разрешения и защита данных

- Агентам разрешены анализ, изменения в изолированной ветке, локальные/синтетические тесты, подготовка PR и отчёта в пределах задачи.
- Запрещены без отдельного одобрения: merge в master, релиз/деплой, изменение реальных Drive/Calendar/Abacus, удаление/перезапись пользовательских данных, публикация секретов, обход branch protection.
- Публичный репозиторий: только синтетические фикстуры и обезличенные логи. Секреты не помещать в задачи, комментарии, diff и отчёты.
- При параллельной работе — отдельные branch/worktree/cloud environments. Слияние и разрешение конфликтов выполняются через проверяемый PR.

## Границы решений

Агент может принимать обратимые технические решения в рамках принятых ограничений. Он не может «поправить» требование под написанный код, менять canonical архитектуру без согласования или считать закрытую техническую задачу принятым продуктовым решением.

См. [portable task history](../tasks/README.md) и [execution protocol](../orchestration/README.md).
