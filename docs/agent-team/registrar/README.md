# Task Registrar — единая выдача номеров TASK-NNNN

**Состояние:** MVP в TASK-0003; заработает только после утверждения и merge PR в master. **Это только регистрация; запуск Claude/Codex ещё не подключён.**

## Зачем

Claude и ChatGPT одновременно предложили TASK-0002. При этом TASK-0002 уже был создан Claude в PR #13, но не существовал в master, поэтому поиск папок только на master не помогал. Регистратор резервирует номер **до создания рабочей ветки**.

## Канонические файлы

- `docs/agent-team/tasks/registry.json` — список уже зарегистрированных или зарезервированных заявок с idempotency key, ID и slug; переносимый реестр, не заменяющий task.md.
- `docs/agent-team/tasks/active/TASK-NNNN_slug/task.md` — задача, создаваемая регистратором в статусе `draft`.
- `docs/agent-team/tasks/completed/` — принятый архив.
- `scripts/agent-team/register_task.py` — локальный API, не зависит от GitHub и может быть использован в другом окружении.

Начальные записи в registry.json: TASK-0002 занята в PR #13; TASK-0003 — этот PR. ID TASK-0001 уже существует в completed/. По окончании bootstrap следующий автоматический ID — TASK-0004.

## Вызов после merge

В GitHub открыть **Actions → Register portable agent-team task → Run workflow**, выбрать `master`, заполнить:
- `request_key` — постоянный уникальный ключ заявки (одинаковый при повторной попытке, например `request-20261116-notes-1`).
- `slug` — английский kebab-case, например `calendar-import-recovery`.
- `title` — понятное название задачи без приватной информации.
- `requester` — идентификатор роли или автор.
- `source` — необязательная ссылка на обсуждение/одобренный запрос.

Workflow принимает заявку только на `master`, проверяет реестр и создаёт папку задачи + обновление реестра **одним commit** в master. При повторении `request_key` возвращает ранее выданный ID, не создавая вторую задачу. Если `request_key` переиспользован с другими title/slug, отказ.

## Конкуренция

Workflow использует `concurrency: queue: max` и `cancel-in-progress: false`; внутри повторно загружает master, выделяет максимальный ID из резервирований и папок и делает **только fast-forward** push. Если head изменился, получает новый head и заново выделяет ID. Поэтому два успешных коммита не могут занять один номер, даже при гонке. Если очередь переполнена или закончились попытки push, задача **не зарегистрирована** — это видимая ошибка, требующая повтора с тем же `request_key`.

**Примечание о branch protection:** GitHub Actions `GITHUB_TOKEN` может не иметь права push в защищённый master. Не отключать protection ради удобства; регистратор должен завершиться ошибкой. В этом случае выбрать отдельную GitHub App с узкими правами или последовательную регистрацию через отдельный утверждаемый PR. Установка прав — решение Product Owner.

## Политика для агентов

1. Агент предлагает задачу и получает согласование в разговоре; запрос регистрации должен иметь стабильный `request_key`.
2. Только registrar присваивает очередной ID; Claude/Codex не создают самостоятельно папки `TASK-NNNN_...` в рабочих ветках.
3. После регистрации задача **draft**. До смены на ready нет разрешения её исполнять.
4. Любые доработки существующей задачи — отдельная ветка/PR, техническая история остаётся в task.md, discussion/ и result.md.
5. GitHub Action — adapter. При смене GitHub выполняем тот же Python скрипт в транзакционном single-writer процессе с проверкой версий.
6. Запись через штатный `GITHUB_TOKEN` сама по себе не запускает другие GitHub Actions; никакой dispatch исполнителей не считается включённым. Для будущих cloud adapters надо отдельно проверить API, permissions, события, budget и retry.
