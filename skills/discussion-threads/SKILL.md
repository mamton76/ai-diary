# Discussion Threads — проектные обсуждения по тредам

## 1. Назначение

Этот skill нужен, когда вопрос нельзя честно закрыть одной фразой и полезно сохранить:

- исходную формулировку;
- варианты;
- аргументы;
- реплики пользователя;
- позиции разных агентов;
- новые факты, найденные позже;
- снятые решения;
- окончательное решение;
- место, куда это решение было перенесено.

Главный принцип:

> **Текущее состояние живёт в source-документе. История рассуждения живёт в треде.**

Тред не заменяет PRD, requirements или architecture. После принятия решения соответствующий source-документ обязательно обновляется.

## 2. Когда включать skill

Использовать для:

- пунктов из `open-questions.md`;
- спорных продуктовых требований;
- архитектурных развилок;
- вопросов, где есть два и более разумных варианта;
- решений, которые могут быть пересмотрены;
- обсуждений между пользователем, ChatGPT/Codex и Claude Code.

Не заводить тред для:

- простой справки;
- факта, который можно проверить без выбора;
- мелкой редакторской правки;
- задачи, где решение уже явно принято;
- сырого исследования, в котором ещё даже не сформулированы варианты.

Если вариантов ещё нет, сначала исследовать вопрос и только потом создавать тред.

## 2.1. Два режима фиксации

У треда есть два режима. Они используют одну и ту же структуру вопроса, статусов, решений и source-синхронизации, но по-разному фиксируют обсуждение.

### Письменный режим (`written-turns`)

Использовать, когда обсуждение идёт обычными текстовыми сообщениями и важна точная история аргументов.

- сохранять ход за ходом;
- использовать speaker labels (`пользователь —`, `ChatGPT —`, `Claude —`);
- реплики пользователя переносить максимально близко к исходной формулировке;
- не переписывать уже записанные реплики задним числом;
- сохранять правило очереди и `Нужно от пользователя`.

### Голосовой режим (`voice-summary`)

Использовать, когда вопрос обсуждается голосом или разговор идёт свободно и дословная стенограмма создаст шум.

- **не стенографировать разговор**;
- не переносить случайные обрывки, оговорки и фоновую речь;
- после содержательного куска разговора добавлять компактную сводку: какие варианты появились, какие аргументы важны, что уточнилось, что осталось открытым;
- не приписывать пользователю решение или позицию сильнее той, которую он реально выразил;
- если пользователь явно сформулировал важное требование или решение, его можно привести близко к оригиналу;
- решение фиксировать только после явного согласования;
- `Нужно от пользователя` использовать только когда разговор действительно остановился на конкретном выборе; не вставлять placeholder после каждой голосовой реплики.

Для обоих режимов в metadata треда указывать:

```markdown
**Режим фиксации:** written-turns
```

или

```markdown
**Режим фиксации:** voice-summary
```

Режим можно сменить по ходу одного треда. При смене добавить короткую отметку внутри `## Обсуждение`, не переписывая уже сохранённую историю.

## 3. Source-документ и sibling-каталог

Для документа:

```text
docs/baseline/04-open-questions.md
```

обсуждения живут рядом:

```text
docs/baseline/04-open-questions.threads/
```

Общее правило:

```text
<document>.md
<document>.threads/
```

Папка тредов **опциональна**. Она появляется только когда хотя бы один пункт действительно начинает обсуждаться.

В source-документе у активно обсуждаемого пункта добавляется ссылка:

```markdown
**Обсуждение:** [тред](04-open-questions.threads/01_PQ-001_source-of-truth/00_thread.md)
```

Не создавать пустые треды для всех вопросов заранее.

## 4. Древовидная структура

Каждый обсуждаемый вопрос — отдельный узел-папка:

```text
04-open-questions.threads/
  00_index.md

  01_PQ-001_source-of-truth/
    00_thread.md

  02_PQ-003_minimum-web/
    00_thread.md

    01_SQ-01_mobile-scope/
      00_thread.md

    02_SQ-02_revision-ui/
      00_thread.md
```

Правила:

- верхний уровень соответствует исходному вопросу из source-документа;
- вложенная папка — подтема, которая стала самостоятельным выбором;
- не дробить тред заранее: подтред появляется только когда основной вопрос реально распадается;
- желательно не уходить глубже 2–3 уровней;
- номер `NN` задаёт порядок появления внутри родителя;
- ID source-вопроса сохраняется в имени верхнего узла;
- для локального подтреда можно использовать `SQ-01`, `SQ-02` и т. п.;
- slug короткий, стабильный, в kebab-case;
- статус не кодируется в имени файла/папки: он живёт в index и внутри thread.

## 5. `00_index.md`

Корень `*.threads/` содержит индекс.

Минимальная таблица:

```markdown
| № | ID | Вопрос | Статус | Чей ход | Тред | Куда переносим решение |
|---|---|---|---|---|---|---|
| 1 | PQ-001 | Canonical source of truth | обсуждаем | пользователь | [тред](...) | 03-product-baseline.md |
```

Статусы:

- `обсуждаем`;
- `ждём пользователя`;
- `ждём исследования`;
- `заблокирован`;
- `решён`;
- `отложен`;
- `снят`.

Индекс отвечает на вопрос «что сейчас происходит по всему набору обсуждений».

Сам тред отвечает на вопрос «почему мы пришли к этому состоянию».

## 6. Формат `00_thread.md`

Базовый шаблон:

```markdown
# PQ-001 — Что считается canonical source of truth?

**Источник:** [04-open-questions.md / PQ-001](../../04-open-questions.md#...)
**Статус:** обсуждаем
**Родитель:** —
**Дочерние треды:** —
**Куда переносим решение:** ../03-product-baseline.md

## Вопрос

<исходная формулировка; не переписывать её так, чтобы поменялся смысл>

## Варианты

1. ...
2. ...
3. ...

## Контекст

<факты, ограничения, ссылки; это не место для подмены решения>

## Обсуждение

ChatGPT — ...

Claude — ...

**Нужно от пользователя:** выбрать между A и B / подтвердить критерий / ответить на вопрос.

пользователь —

**Решение:** —
```

## 7. Жёсткий порядок внутри треда

Верхняя часть — metadata, вопрос, варианты, контекст.

`## Обсуждение` всегда идёт после контекста.

`**Решение:** ...` — **последняя непустая строка файла**.

Новые реплики вставляются **перед** строкой решения.

Не добавлять после решения секции «Update», «Notes», «P.S.» и т. п.

Если появилось новое знание — это новая реплика внутри обсуждения.

## 8. Реплики и авторство

Следующие правила относятся прежде всего к режиму `written-turns`. В режиме `voice-summary` вместо покомпонентной фиксации реплик используются датированные/последовательные смысловые сводки; дословная стенограмма не требуется.

Использовать явные speaker labels:

- `пользователь —`;
- `ChatGPT —`;
- `Claude —`;
- `Codex —`;
- при необходимости `агент (<имя>) —`.

Правила:

1. Реплику пользователя переносить из чата максимально буквально; не приписывать ему более сильную позицию, чем он высказал.
2. Уже записанную реплику пользователя не переписывать задним числом.
3. Агент может исправить собственную фактическую ошибку новой репликой, но не стирать историю.
4. Исследование или новые данные записываются как:
   `ChatGPT — **обновление (<дата>):** ...`
5. Если второй агент не согласен, он пишет отдельную аргументированную реплику, а не переписывает реплику первого.

## 9. Правило хода

Агент не закрывает спорный проектный вопрос от имени пользователя, если пользователь явно не делегировал ему это решение.

После своей содержательной реплики агент обычно оставляет:

```markdown
**Нужно от пользователя:** <одна конкретная вещь>.

пользователь —
```

Это означает «ход пользователя».

Если ничего от пользователя не нужно, например тред заблокирован исследованием:

```markdown
**Нужно от пользователя:** ничего; ждём результат исследования AQ-X.

пользователь —
```

После принятого решения placeholder удаляется.

## 10. Решение

Пока договорённости нет:

```markdown
**Решение:** —
```

Когда выбор принят:

```markdown
**Решение:** [принято] (2026-09-26) Канонические пользовательские данные хранятся ...
```

Допустимые outcome tags:

- `[принято]`;
- `[отложено]`;
- `[не требуется]`.

Решение должно отвечать на вопрос целиком. Если остался самостоятельный хвост, его следует вынести в дочерний тред или новый open question.

## 11. Пересмотр решения

Старое решение **не стирается**.

Если появились новые факты и вопрос переоткрыт, прежняя строка остаётся в истории:

```markdown
**Решение (снято, 2026-10-03):** [принято] (2026-09-26) ...
```

После неё продолжается `## Обсуждение`, а в самом низу снова:

```markdown
**Решение:** —
```

Действующее решение всегда одно и всегда последнее.

## 12. Где живёт итог

Чтобы source и discussion не разъехались:

- **тред** хранит rationale, варианты, аргументы и историю пересмотров;
- **source-документ** хранит текущее принятое состояние;
- после решения агент в том же рабочем заходе обновляет source-документ;
- в source-документе остаётся ссылка на тред как на decision history;
- если решение порождает requirement или architecture rule, обновляется именно соответствующий документ, а не только `open-questions.md`.

Пример после закрытия:

```markdown
## PQ-001 — Что считается canonical source of truth?

**Статус:** РЕШЕНО  
**Решение:** user-owned files являются canonical data; DB допустима как rebuildable operational projection.  
**История обсуждения:** [thread](04-open-questions.threads/01_PQ-001_source-of-truth/00_thread.md)
**Перенесено в:** [Product baseline](03-product-baseline.md#...)
```

## 13. Один вопрос — один канонический тред

Если тот же вопрос всплыл:

- в другом документе;
- в архитектурном review;
- у второго агента;
- в PR;

не создавать параллельную историю решения.

Найти существующий тред и добавить ссылку на него.

Если новый контекст действительно меняет вопрос, создать дочерний тред или новый ID и связать их явно.

## 14. Работа двух агентов

Перед ответом в существующем треде агент должен прочитать:

1. source-пункт;
2. весь `00_thread.md`;
3. index;
4. родительский тред, если он есть;
5. уже принятые дочерние решения, которые влияют на вопрос.

Правила:

- не объявлять позицию другого агента по памяти;
- не «схлопывать» разногласие между ChatGPT и Claude без пользователя;
- если обе позиции полезны, оставить обе и сформулировать пользователю конкретный выбор;
- не дублировать одинаковое исследование без причины;
- новая внешняя проверка должна быть помечена как новое evidence, а не как будто это было известно с начала.

## 15. Создание подтреда

Подтред нужен, если:

- один вопрос содержит два независимых решения;
- один из вариантов требует отдельного исследования;
- решение дочернего вопроса блокирует родительский;
- тред разросся так, что пользователь вынужден каждый раз восстанавливать несколько независимых контекстов.

В родительском треде добавить:

```markdown
**Дочерние треды:**
- [SQ-01 — Нужны ли manual edits canonical files?](01_SQ-01_manual-edits/00_thread.md)
```

И явно отметить зависимость в обсуждении.

## 16. Операционный workflow

Когда пользователь говорит «давай обсудим PQ-001»:

1. найти source-вопрос;
2. **свежо перечитать index/source и проверить весь sibling-каталог по QUESTION-ID**, существует ли canonical thread; не полагаться на память текущего чата;
3. если thread уже создан другим чатом/агентом — использовать его, а не создавать второй;
4. если нет — создать node folder и `00_thread.md`; порядковый `NN` — только display/order, identity задаёт QUESTION-ID;
5. добавить ссылку из source-пункта;
5. обновить `00_index.md`;
6. прочитать имеющийся контекст;
7. добавить реплику агента;
8. оставить одно конкретное `Нужно от пользователя`;
9. в `written-turns` перенести содержательную реплику пользователя в thread; в `voice-summary` после содержательного фрагмента разговора записать смысловую сводку;
10. продолжать до решения;
11. зафиксировать решение;
12. обновить source-документы;
13. обновить index.

### Параллельные чаты и агенты

При параллельной работе нескольких чатов/агентов возможна гонка: оба видят, что треда ещё нет, и пытаются создать его одновременно. Поэтому перед созданием нужно повторно проверить QUESTION-ID в index/source и sibling-каталоге. Если обнаружены два треда одного QUESTION-ID, не продолжать обсуждение в обоих: выбрать один canonical thread, перенести уникальный контекст и исправить ссылки.

## 17. Минимальная проверка перед коммитом

Для изменённого треда проверить:

- вопрос имеет устойчивый ID;
- source link существует;
- speaker labels не потеряны;
- пользовательские реплики не переформулированы;
- нет двух действующих решений;
- действующее `**Решение:**` — последняя непустая строка;
- если тред открыт, понятно, что именно нужно от пользователя;
- если тред решён, source-документ обновлён;
- index соответствует статусу;
- нет второго треда про тот же выбор.

## 18. Будущее развитие

В первой версии skill намеренно файловый и без скриптов.

Позже можно добавить:

- lint структуры;
- автоматическую сборку index;
- проверку битых links;
- вывод «чей ход»;
- поиск дубликатов ID;
- проверку, что решённый тред отражён в source-документе;
- сборку decision log.

Если автоматизация потребует изменения формата, существующие треды не мигрировать молча: сначала зафиксировать решение о миграции.
